# Task2 preflight — secure collection invitations

Existing approved Phase09 plan/spec§7 is authority. This is design preparation during Task1's serial built-browser regression, not Task2 completion or live mail activation.

- Interfaces: createInvitation, acceptInvitation, revokeInvitation, plus authorized pending-list for eventual UI. Creator must be actual current Owner/Admin; only Owner may invite Admin. Role cannot be OWNER or supplied as actor authority. Viewer/Editor cannot create or revoke invitations.
- Invitation membership is separate from granular share rights. A Viewer cannot be promoted by a link. Membership revision CAS and exactly-one canonical owner remain enforced in the accept transaction.
- Generate32crypto-random bytes, base64url43chars; persist only SHA256 hash. Intended normalized email or immutable target user ID; email-bound acceptance requires a currently verified matching account. No password/token/email in public errors/logs. Raw token returned once only to authorized creator for the link; no SMTP/provider activation or delivery claim.
- Expiry defaults48hours, bounded up to14days; time checked in DB UTC, not caller clock. Revocation/expiry/acceptance checked under locks. Limit20pending invites per collection initially; bounded transaction budgets and no external I/O while locked.
- User identity locks precede collection/invitation locks; creator role must still authorize the requested grant at acceptance. A removed/demoted inviter or old-Owner-to-Admin change cannot leave an Admin escalation invitation valid. Existing membership should never be silently overwritten/demoted/promoted by acceptance; return controlled conflict/idempotent accepted state as appropriate.
- Concurrent acceptance consumes one token once; exact same recipient may retry idempotently, different user cannot. Existing Owner stays derived, never inserted as a member. Role change/parent deletion/recipient email verification changes require current DB authority, no stale cookie/role claims.
- Creator/recipient actor IDs must respect actual account erasure. Private invite targets/tokens are deleted with parent/target as appropriate; preserve no unnecessary personal evidence. New additive migration only, prior030000–036000 remain frozen.
- REST: authenticated POST create under /api/v1/collections/[collectionId]/invitations, same-origin/content-type/bounded body/no-store consistent with current route factories. Accept/revoke routes and domain native integration witnesses; UI later Task7. Closed400/403/404/409/503/500 boundaries, no SQL or roster leaks.
- Required RED witnesses: wrong verified email recipient, unverified matching account, expired/revoked token, Viewer/Admin grant bounds, current inviter demotion, simultaneous accepts, membership capacity/stale CAS, token hash only, outside-scope privacy and same-origin HTTP transport. No fake recipient, real outbound mail or real customer mutation.
