## Behavior and transaction boundaries

- `createMediaCleanupService(database, {retentionHours, batchSize?})` exports `unlinkAsset(actorUserId, target, linkId, itemId?)`, `findDeletableAssets`, and deletion/reconciliation repository operations. Supported targets are ITEM, ITEM_DOCUMENT and AVATAR. Unlink is owner-scoped and transactional; absent/foreign/already removed links return LINK_NOT_FOUND. Item unlink follows existing item-before-asset locking.
- New authenticated same-origin DELETE routes: `/api/v1/items/[itemId]/media/[linkId]`, `/api/v1/items/[itemId]/documents/[linkId]`, `/api/v1/media/avatar`. Success is 204 with no-store; foreign/invalid link IDs are hidden with 404. No Task6 UI added.
- Additive migration `20261017120000_media_cleanup` supplies orphan/cleanup/attempt timestamps, independent permanent key tombstones and reference triggers. BEFORE triggers lock affected assets in UUID order and deny reference creation once cleanup starts. AFTER triggers update orphan state transactionally across media links, private document links, avatar replacement/removal and cascades. Soft-deleted parents retain their links and count conservatively for restoration. Existing unlinked assets begin retention at migration time; new unused/abandoned uploads begin at creation. Final unlink restarts retention. The split transaction prelocks its complete media/document asset set in deterministic UUID order before either bulk insertion.
- Cleanup rechecks every reference under the asset row lock, marks cleanup started and commits tombstones before deleting bytes. The existing dedicated-session advisory namespace spans ordinary processing/cleanup storage work. Byte failure leaves asset, variants and durable keys retryable. Asset rows disappear only after every tracked original/variant byte deletion succeeds. Missing bytes remain idempotent. Processing claims/renewals/reservations and original upload completion exclude cleanup-started rows; reads explicitly exclude them and continue requiring live references.
- A dead DB session cannot fence unbounded old storage I/O. Tombstones include the original, every recorded variant and all three deterministic derivative keys, remain after asset/variant deletion, have no FK/owner payload and never expire on a timer. A bounded periodic reconciliation pass removes any late publication. UUID-generated keys are never reused. Asset attempts and tombstone checks rotate in oldest-attempt/check order, including failed deletions, to avoid starvation.
- The actual worker starts cleanup after the queue and drains it before image dispatch, queue teardown and database disconnect. Polling starts immediately, suppresses overlapping local scans and retries later after failures. No manual-only cleanup path.

## Explicit controller rulings and costs

Approved in this run before implementing policy: MEDIA_RETENTION_HOURS=168, MEDIA_CLEANUP_INTERVAL_MS=60000, MEDIA_CLEANUP_BATCH_SIZE=100, STORAGE_TEMP_MAX_AGE_HOURS=24. All are validated positive bounded integer environment settings, documented in .env.example and forwarded by Compose. Retention/temporary-age bounds are 1–87600 hours, poll 1–86400000ms, batch 1–1000. Costs if defaults are wrong: storage persists longer or is reclaimed earlier after unlink, and scans run more/less often; future configuration changes are reversible but completed byte deletion is not. No restoration promise after retention expiry.

Controller approved reuse of the existing dedicated-session locker for `staging:<UUID>` as well as final assets. LocalPersistentStorage takes an optional constructor locker without changing the four-method StorageProvider contract. All production web/worker constructions provide it. The writer acquires it before staging creation and holds it through rename/finally cleanup; the sweeper acquires the same namespace and rechecks age before unlinking. An in-process active set is an additional safeguard, not cross-process proof. Observed session loss retains the existing fail-closed process-abort behavior. A server-side lock loss may make an ancient in-flight upload fail to rename; that is permitted and cannot successfully link missing bytes. Final-key late publication remains discoverable through permanent tombstones.

Reserved legacy `.storage-UUID.tmp` files are swept conservatively after 24 hours; symlinks, nonreserved names and fresh staging are preserved. **Rollout precondition:** stop all old web/worker writers before starting the upgraded cleanup worker against the shared volume; every subsequent writer must use the upgraded staging-lock implementation. This is also documented beside the environment settings. A pre-lock live writer cannot be distinguished safely merely from the legacy filename. Cost: coordinated service replacement during upgrade. PID checks and age alone are deliberately not treated as live-write exclusion.

Routine bounded traversal choice reported to controller: production maintenance processes at most 1000 filesystem entries per poll and resumes a cursor; process restart restarts enumeration safely. Cost: large trees need more polls. Directory enumeration uses readdir (one directory's entries may be materialized); no directory descriptor stays open across polls. Existing trusted app-owned filesystem boundary and deferred directory-fsync/power-loss follow-up remain unchanged.
