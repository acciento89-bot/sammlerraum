## Behavior and boundaries

- Saved item editor has a gallery and document manager, outside the item form to avoid nested forms. Unsaved items explain that saving is required first. Gallery supports drag ordering, keyboard-accessible move buttons, title selection, removal, file progress/cancel, loading/retry and pending/processing/failed states. Failed processing asks for unlink/re-upload after worker retries stop.
- Documents default PRIVATE, independently of item visibility. Upload category and visibility are deliberate controls; linked documents can change category/visibility and download through protected media routes or unlink. Unlisted remains protected under the existing Task4 policy, accurately explained in both languages. JPEG/PNG/WebP images, PDF/image documents and configured byte limits use client guidance plus existing server signature/decode/size enforcement. No storage keys or server paths are rendered.
- Owner-only GET `/api/v1/items/:itemId/media` returns bounded, explicitly selected safe link/asset DTOs and configured upload limits, no-store. PUT at the same path accepts a complete gallery-link order; PATCH `/documents/:linkId` accepts an explicit validated category and visibility. Existing authenticated same-origin uploads/link/unlink APIs remain in use. Mutations check exact Origin before parsing; sessions bypass cookie cache. Absent/foreign item/link IDs remain hidden with 404. Reorder rejects duplicates, omissions and foreign membership before any position update; item row locking serializes reorder/link/unlink and all position writes commit atomically.
- Controller ruling: the first GALLERY link whose asset kind is IMAGE, by position (id tie-break for legacy ties), is the title image. Selecting title moves that link to the front with every other relative order preserved in the same transaction. There is no independent cover field. Cost: selecting a title changes gallery order, and moving the first image changes the title; the state cannot drift between two cover representations. Existing split copying of link positions/purpose/title/visibility is unchanged.
- Routine boundedness choice: each image/document target accepts at most 200 links; owner/public lists take 200, request bodies and reorder arrays are bounded. New links check the target count while holding the item lock. Cost: large collections require unlinking before attaching beyond that per-item limit; legacy data above 200 would require later pagination rather than silent reordering. No migration or persisted schema change was required.
- Item page distinguishes owner editing from a minimal anonymous/foreign read-only view. The authoritative public item query checks actual collection/node ancestry and activity; public projection shows only item title, public description and READY gallery image derivative URLs with item-title alt text. It contains no document list, owner filenames, private notes, acquisition or location metadata. It is dynamic and noindex/nofollow. Task4 reauthorizes each image read and denies originals to nonowners; a public item never promotes a private receipt.
- Cancellation aborts an in-flight binary request, leaving any server-recorded unlinked intent recoverable by Task5 retention. Once a link request starts, the client observes its result; cancellation unlinks its successful link before reporting canceled. Failed undo reports an error and reloads actual links, never a success. Unmount uses the same cancellation path. A lost network response can leave a server-committed link visible after reload for explicit removal; successful unlink does not delete retained/shared bytes.
- Touched inherited M1: item-link now locks the asset after the item, then checks cleanupStartedAt under the lock. A concurrently committed cleanup claim therefore yields ASSET_NOT_READY/domain 409 rather than reaching the reference trigger as an unhandled persistence error. Database reference guards remain. Avatar caller's analogous minor remains deferred; no unrelated item INTEGER/location ancestry changes.

## Review fix round 1 — I1 filename transport and media fixture isolation

Original reviewed implementation: `cfdea251bf82609f49d30e7a957eeb0cada87156`; original evidence commit: `30ff3e072ab11515de3353e665a8381cfb00a6d8`. Scoped fix source: `5319a745a852068508ef509314477c2e078ab123`. No unrelated auth, UI design, database schema or plan changes.

I1 cause: raw File.name in XMLHttpRequest.setRequestHeader requires a ByteString; non-Latin-1 characters throw before send. The new uploader encodes the filename once with encodeURIComponent and marks it with `x-file-name-encoding: percent-utf8`. The shared contract documents the marker. The server decodes exactly once only with that marker; absent-marker legacy clients retain literal filename/percent semantics. Unknown encoding, malformed escapes/UTF-8, encoded names above 2295 characters and decoded names above the existing 255 UTF-16-unit limit return safe 400 before body consumption/persistence. The domain reuses the shared 255 bound and retains its existing slash, backslash, control-character and empty-name rejection. This avoids silently double-decoding a legitimate percent sequence. No filename is used as a storage key.
