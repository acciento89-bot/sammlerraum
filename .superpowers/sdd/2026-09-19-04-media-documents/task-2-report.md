# Phase 04 Task 2 — media/document upload and link foundation

## Implemented

- Additive `20260927140000_media_documents` migration defines `MediaAsset`, `MediaVariant`, `MediaLink`, `DocumentLink`, enums, owner-scoped composite foreign keys, and a profile avatar foreign key. Asset and variant parent FKs use `RESTRICT`: deleting a user or asset cannot silently erase the final key tracking stored bytes. Item hard deletion can cascade its links but leaves the asset record; normal item deletion is soft deletion. Asset cleanup must remove bytes before removing its rows, and avatar references must be cleared first.
- Existing pre-media `UserProfile.avatarAssetId` could be an arbitrary UUID, with no prior media table or bytes. Migration clears these unsupported pointers before adding the FK. It preserves all other profile fields. An isolated PostgreSQL migration replay test inserts such a legacy pointer and checks the repair and new FK.
- `createMediaService` validates JPEG/PNG/WebP image uploads with file-type magic and full Sharp decode, checking byte and pixel caps before persistence. PDF is accepted only as a document, with signature and EOF checks. Document uploads accept these same image types. Claimed MIME and filename extension must match detection. Default limits: 20 MiB image, 25 MiB document, 40 million pixels; server configuration accepts positive bounded overrides (100 MiB / 100 million maxima). SVG/HTML/other active types are not allowed.
- Commit `MediaAsset(status=UPLOADING, storageKey=originals/<UUID>, checksum, size, MIME, dimensions, filename)` before the storage write. After the write, PDF becomes `READY`; any image MIME, including image-backed documents, becomes `PENDING`. An exception in storage or the following DB update leaves a durable, discoverable `UPLOADING` record. Link failures leave the asset and bytes tracked. The API returns an asset DTO without storage keys.
- `linkAsset` locks an owned, nondeleted item row in a transaction, verifies an owned linkable asset, and inserts an ordered gallery/detail or categorized document link. Documents default to `PRIVATE`. Unknown catalog targets are rejected. Composite FKs independently prevent linking a foreign asset/item. Splitting a quantity item copies all media and document link metadata inside the same locked transaction while sharing asset IDs and bytes.
- Profile upsert/update validates a READY owned image before accepting an avatar ID. The composite FK prevents cross-owner assignment and makes avatar use a live reference for cleanup.
- Owner-only mutation routes: `POST /api/v1/media/images`, `POST /api/v1/media/documents` take a raw binary body, `Content-Type`, and `X-File-Name`; `POST /api/v1/items/:itemId/media` takes `{assetId,purpose,title?}`; `POST /api/v1/items/:itemId/documents` takes `{assetId,category,visibility?,title?}`. They enforce exact Origin and fresh uncached session, return `no-store`, cap uploads while streaming irrespective of absent/lying Content-Length, and never expose a storage path. Task 6 adds gallery reordering/title and document editing/removal UI/API controls.

## Task 3–6 handoff

- **Task 3 dispatcher:** `MediaAsset.status=PENDING` is the durable queue intent for every image MIME, regardless of `kind`. Poll/dispatch pending rows even after queue outages; queue enqueue errors must leave them recoverable. Transition to `PROCESSING` with an atomic claim, reclaim stale `PROCESSING` by `updatedAt` after worker crashes, and make variant writes idempotent (`MediaVariant` unique `(assetId,name)`). Required stored names are `THUMBNAIL`, `MEDIUM`, `LARGE`. Compute variant bytes/metadata, create a durable variant storage-key record before writing each variant, then write; only set asset `READY` after all required sanitized variants are valid. On permanent failure use `FAILED` with an explicit retry policy. The worker Docker image must include Sharp's native runtime dependencies and supported platform binaries.
- **Task 4 delivery:** Public image bytes may come only from sanitized `MediaVariant` records, including image-backed documents; the original remains owner-authorized. A PDF document marked public can follow document visibility and ancestry authorization, with safe download headers. A UUID alone gives no read access. Never expose `storageKey` in a public DTO. `PENDING`/`PROCESSING`/`FAILED` lack public variants until completion.
- **Task 5 cleanup:** Inspect stale `UPLOADING` rows and their `storageKey` with `storage.exists`; these may represent a failed put or a completed put whose status update failed. Use a conservative age threshold to avoid active writes. Count media/document links and `UserProfile.avatarAssetId` as live references. Unlinked retained assets, their variants, and originals require byte deletion before record deletion, with retryable status/order. Parent/asset FK `RESTRICT` prevents silent loss of tracking through user or asset deletion. Coordinate with Task 3 claims so cleanup cannot race variant generation or resurrect deleted media.
- **Task 6 UI:** use upload `asset.id`, `status`, and explicit link endpoint; support progress/cancellation and `PENDING`/`FAILED` presentation. The item split copies link positions, titles, purpose, category, and visibility into both portions and shares assets.
