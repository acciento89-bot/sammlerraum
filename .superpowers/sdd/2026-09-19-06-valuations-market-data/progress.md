## Contract observations and pending design decisions

- Existing purchase currency validation supports the runtime ISO currency set, rather than a five-currency list. Reuse or deliberately factor this boundary; do not narrow existing item contracts accidentally.
- Canonical money must parse localized grouping and decimal separators without floating point. Clarify currency exponent, allowed signs, input limits, PostgreSQL bigint range and JSON string transport. Cover zero- and three-decimal currencies as well as DE/EN EUR. Inspect all legacy purchase-price consumers before changing their behavior.
- Manual valuations append actor-bound private history. Define ownership, lifecycle, observed-time validation, pagination, quotas and item locking consistently with existing services. Avoid a separate generic audit framework; Phase 09 owns shared audit integration.
- Resolve whether a manual estimate is per interchangeable unit or an entire quantity row before defining storage and split behavior. Existing purchase values are explicitly per unit; spec 5.5 permits quantity rows only for interchangeable facts. Preserve historical observation provenance when splitting, without silently inventing an estimate on a newly created item or changing the meaning of a prior row as quantity changes. This is an open preflight question, not an approved copy policy.
- External observations are global catalog facts and must never incorporate private item purchase, condition or grading data implicitly. Keep provider/kind/currency and authored qualifiers explicit.
- The plan describes both provider/external-ID idempotency and observation-time identity. Resolve this before schema implementation: sale IDs can identify one event, while current guide product IDs recur across polling cycles. A retry must retain its observation identity; repeated successful future polls must not collapse all history. Do not derive fresh retry identity from Date.now().
- Distinguish upstream observed time from retrieval time. If a provider has no observation timestamp, expose the documented fallback provenance honestly rather than invent a historical sale date.
- Variant matching must use explicit identifiers and qualifiers against an authoritative coherent catalog snapshot. Decide how retirement and catalog revision changes affect queued requests. A weak title match must not attach a price silently.
- Source comparison remains unaggregated until an explicit aggregation/FX policy exists. Even a single currency does not justify blending different price kinds or providers. Missing data stays missing.
- Production adapters require current primary API and licensing documentation when their task is reached. The plan names Scrydex and PriceCharting; no paid call, scraping, account provisioning or credential request is needed for fake-HTTP implementation and CI.
- PriceCharting's configured-token limiter must hold across actual worker concurrency, not merely within one adapter object. Redact credentials from URLs/errors/logs. Decide scheduling/producer ownership and disabled-by-default behavior before claiming real scheduled synchronization.
- UI tests must be registered in the actual desktop/mobile Playwright projects and production CI command. Reuse the Phase 05 DE/EN matrix and source-separated presentation, with exact formatting that cannot lose bigint precision.

## Existing seams inspected (preparation only)

- `packages/contracts/src/items.ts`: purchase amount is currently a nonnegative safe JS integer; currency uses `Intl.supportedValuesOf("currency")`; fields must be supplied or cleared as a pair. New bigint valuation contracts must use explicit decimal strings at JSON boundaries without silently changing this established purchase contract.
- `apps/web/src/components/items/item-form-values.ts`: existing purchase/custom-money input accepts a single decimal comma or dot and disallows grouping; exact conversion uses BigInt internally then checks MAX_SAFE_INTEGER. New locale-aware valuation parsing is a separate feature, not proof that this existing helper already meets grouped-input requirements.
- `packages/domain/src/grading/grading-service.ts`: actor-bound service, ReadCommitted transactions, item row lock through collection ownership, hidden foreign/deleted 404, inactive writes rejected, bounded personal records. Reuse the pattern while deciding valuation-specific append/history and split semantics explicitly.
- Actual worker composition lives in `apps/worker/src/run.ts`; `main.ts` owns lifecycle/health. Queue handlers register before runtime start. Runtime already starts/stops image dispatch and media cleanup via lifecycle hooks. A new market handler alone does not establish a bounded producer/schedule or shutdown behavior.
- `packages/queue/src/*` has an exclusive persisted queue and singleton-key client. Queue duplicate suppression is not a substitute for immutable observation identity in the database; later recurring jobs need new poll identities while retrying one job retains its original identity.

These are preparation notes and unresolved integration questions, not extra approved product scope. Task briefs, fresh implementers, task reviews, exact-source CI, canonical checkoff and main ledger-only sync remain sequential after the Phase 05 gate.
