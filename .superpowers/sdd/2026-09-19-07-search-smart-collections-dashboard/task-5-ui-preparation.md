## 5. URL, raw-f, transport and navigation state

Root direction received during preparation: use one universal private body-query path, with no per-leaf public/private heuristic. Even an ordinary broad search or custom value may contain a serial/certificate/private fact. Therefore the UI must not serialize text or AST into browser URLs, fragments, link hrefs or GET request URLs. Existing GET APIs remain compatible for existing callers, but the new collector UI uses POST equivalents.

Concrete finite prerequisite: POST `/api/v1/search/items` with strict `{text?,f?:string|null,lifecycle?,limit?,cursor?}` and POST `/api/v1/dashboard` with `{text?,f?:string|null,lifecycle?}`. Both call exactly the same existing search/future dashboard service, use fresh session/no-store/requestId and exact APP_ORIGIN, and accept at most32KiB fatal-UTF8 JSON body with unknown/duplicate members rejected through the reviewed bounded body parser. Raw decoded `f` remains a JSON string passed directly to `parseItemFilterJson`; do not JSON.parse then reserialize before the scanner. Nullable/absent f means no filter only in the explicit body contract; GET f=null remains invalid. Preserve existing 16KiB raw/canonical AST, 200-code-point/800-byte text, complexity, response and service limits. No new query persistence backend, second compiler or unbounded parser. Unknown outcome of a read can be retried; a saved mutation cannot be blindly repeated.

Browser URL shape: `/{locale}/search?q=<opaque-random-token>` or dashboard equivalent; saved detail uses saved ID and optional opaque view token. Tokens are fresh random≥128-bit values, not a hash of query data or encoded payload, and never grant server access. Limit/cursor can live inside state too, keeping URL minimal. Use namespaced history.state metadata without overwriting Next's existing keys, and a tab-scoped store containing only bounded normalized query definitions/page state. Concrete bound: ≤20 entries and≤512KiB total, individual stored definition≤32KiB; least-recent eviction may make an older token unavailable, which is shown honestly. Use bounded sessionStorage with memory fallback, not localStorage or server storage; handle disabled storage/QuotaExceeded without losing current controls. Namespace to the authenticated user and clear on logout/401 or detected identity change. Never store returned private item facts, response bodies or auth/session credentials there.

The canonical data model is `{text,filter,lifecycle,limit,cursor?}` (dashboard omits pagination), with canonical filter serialized only after `parseItemFilter` succeeds. Keep unfinished raw input/draft state separate in memory. Reopened saved definitions become typed drafts directly. Raw f exists at transport/parser boundaries, not in a textarea or URL. Malformed/duplicate raw f receives a closed error; do not rescue it by normalizing through JSON.parse first. Unknown browser query keys, malformed encoding, duplicate q, impossible token or old payload-bearing text/f URL show an invalid/unavailable-query state with an explicit Reset action, never silently run default all-owned search. Do not echo the offending URL/raw input in errors.

Apply creates a fresh token/history entry only for a valid new query; pagination creates an entry for that page; canonical housekeeping uses replace rather than adding history. Changing text/filter/lifecycle/limit or replacing a saved revision discards cursor and fetched rows before the new request. Browser Back/Forward restores exactly the token's query and refetches; missing/copied/evicted token shows “This search is not available in this tab” and reset, never the last successful query. Reload restores only a validated same-user tab entry. Navigation between search/dashboard carries a new view token for the same query without transporting values in hrefs. Save creates owned persistence, not a sharing capability: a copied unsaved URL alone cannot reconstruct a query, and a saved URL is still owner-only. This tradeoff is explicit user copy, not an incidental failure.

Native Next transition/history behavior is a proof obligation: do not ship a naive history.replaceState that deletes router keys. Centralize only a narrow `search-url-state.ts` adapter using the supported router/history boundary observed in the installed project, merge its namespaced token metadata, and test push/replace/popstate, locale transitions, reload and direct entry with the actual app. No router/framework upgrade.

## 6. Requests, saved mutations and error recovery

Use a narrow controller/state module patterned on `components/valuations/valuation-state.ts`, with a monotonically increasing generation plus AbortController per search/dashboard/selector channel. Key each result by normalized query token + page + saved ID/revision as applicable. Abort on replace/unmount, but also reject late callbacks by generation (abort alone is insufficient). Snapshot requests started before an acknowledged mutation cannot restore older saved metadata or members. Loading announces status and marks the region aria-busy; do not flash zero/empty before success. On changed query, clear previous results; on same-query refresh failure old results may remain only with explicit stale/read-time warning and no fresh-total claim.

Saved flows:

- List uses bounded Task3 summaries and independent pagination state; Open loads one strict definition, then saved items from `/smart-collections/[id]/items` with limit/cursor only. Do not attach client text/f/lifecycle overrides to resolution.
- Create dialog has name (Task3 normalized1..100 UTF16 units), query summary and Save; persists text+AST+lifecycle, not current result IDs. Explicit all-owned query is valid. Acknowledge returned id/revision first, then refresh list/items. If refresh fails, retain acknowledged saved identity and show refresh failure rather than retrying create.
- Rename/update sends complete replacement and the last fetched expectedRevision. Editing produces a draft until Save; “Save as new” creates a distinct owned saved query. Replacing definition resets saved item cursor even if only the revision changes. Saving does not freeze membership.
- Own stale409: preserve local draft, show conflict, offer Reopen latest or Save as new. Reopen/discard requires explicit confirmation when local edits would be lost. Never silently overwrite using a freshly fetched revision. A user can inspect latest and intentionally reapply edits against that version.
- Delete requires accessible confirmation naming only the owned saved query and explaining that items remain; use expectedRevision. On success navigate to list and clear cached query/results. Foreign/missing/deleted404 are indistinguishable generic unavailable; do not hint at owner/existence.
- SMART_COLLECTION_UNRESOLVABLE409: no members/count displayed as current. Fetch structurally valid detail if permitted; expose selected unavailable references and normal builder repair/removal, then full replacement with expectedRevision. Malformed stored definition cannot be exposed as raw data: show unavailable with list/delete recovery if summary supplies a valid revision. Do not invent an edit fallback from raw corrupt JSON.
- Lost mutation response: mark outcome unknown, keep draft, disable automatic retry, and reload detail/list to reconcile. For create with unknown ID, duplicate names are legal, so name matching cannot prove success; show the owned list and ask user to inspect before creating again. No client-generated idempotency claim absent an actual backend contract. PATCH/DELETE can reconcile latest revision/404 but must not label an ambiguous concurrent change as our acknowledged write.

400 invalid query/filter/cursor: safe local message, preserve draft, offer restart first page for cursor failure only. 401 clears private rendered state/store and offers sign in. 403 same-origin rejection is an action error. 404 saved/reference access is generic. 422 unavailable/reference error rejects the whole query, including unsupported leaves under NOT/OR, with repair action. 413/414 explain too much query data, not zero matches. 503 is temporarily unavailable with explicit Retry. 500 is a generic failure with bounded requestId; never output SQL/cause/raw JSON or console-log bodies. Mutation submit buttons prevent double submit; status text comes entirely from translated keys.
