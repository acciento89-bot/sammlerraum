## 3. Small fixed-envelope duplicate treatment

Proposed private web helper `apps/web/src/lib/api/read-search-body.ts:readSearchBody(request, shape)` supports only five closed shapes: ITEM_QUERY, DASHBOARD_QUERY, COLLECTION_REFERENCES, CUSTOM_FIELD_REFERENCES, CONDITION_REFERENCES. It is not exported as a generic JSON parser. All bodies use `readBoundedBody(request,32768)`, fatal UTF8 decoding and a single linear raw precheck before JSON.parse. Reject a leading BOM explicitly; TextDecoder's default BOM stripping must not hide it. An empty/whitespace-only body or trailing nonwhitespace fails.

Query shapes permit one root object with known scalar values only. Reference shapes below deliberately encode references as arrays of UUID strings or two-element tuples, with no nested objects, so the same fixed shallow scanner suffices:

1. Bound raw bytes before decoding. Scan quoted tokens respecting backslash escapes; JSON.parse of each root key token decodes escape-equivalent keys (e.g. `text` and `t\\u0065xt`) for duplicate detection. Decode/compare keys, not their source spelling.
2. Require a single outer `{}`. Track only root-member expectation and allowed array nesting for the selected shape (zero for query, one for collection IDs, two for reference tuples). Reject any other `{` outside a quoted token. Commas inside arrays never begin object keys. Bound root members by the shape's fixed key count. Reject unknown/duplicate decoded root keys, including prototype-looking keys; never assign keys onto a prototype-bearing record during scanning.
3. Treat f and other quoted values as opaque strings at this stage, including braces/brackets/commas/escaped quotes inside them. Do not cap each outer decoded string at10000 or attempt to parse f here. The entire body is already32KiB. Invalid escape syntax, unescaped control characters, trailing commas, mismatched punctuation, extra roots and malformed numbers are ultimately rejected by JSON.parse; the precheck is deliberately not a second JSON grammar.
4. JSON.parse once after the precheck; strict fixed-shape contract validates root type/scalars, array/tuple lengths, Unicode and IDs. Query values then pass actual raw-f scanner, preserving inner duplicate detection. Reference arrays have the explicit caps below and reject duplicates after lowercase normalization. Error messages never contain the key/value/token/raw parser exception.

Implement a small fixed lexical precheck locally (roughly the existing scanner's string/root-key mechanics), not by adding configuration switches to the filter parser or installing a parser library. Tests must demonstrate escaped-key duplicates and nested f text do not confuse it. JSON.parse with a reviver cannot detect already-overwritten members. This new safeguard applies to5B query/reference bodies only; expanding it to saved mutation bodies is a separately authorized compatibility change.

Body byte cap can reject an AST whose individual raw f is legal but whose escaping plus other fields exceeds32KiB; that is intentional and must be tested/documented, not solved by truncating values or increasing limits. Unsupported media type uses SEARCH_INVALID400 for this helper. Preserve readBoundedBody's existing413 code rather than claiming a new one exists. Fatal UTF8, duplicate keys and malformed JSON normalize to SEARCH_INVALID400; inner filter errors retain their existing closed codes.

## 5. Six routes, three families

Proposed `packages/contracts/src/search-references.ts` contains strict request/response schemas, lowercase UUID normalization, typed DTOs and `REFERENCE_MAX_RESPONSE_BYTES=1048576`. IDs are syntactically checked UUIDs using the existing contract conventions; duplicates are rejected after normalization. A malformed UUID is400; a well-formed inaccessible/missing reference follows the closed semantics below. No arbitrary search string, SQL, owner, requested private field or inventory ID input.

### Collections

- GET `/api/v1/search/references/collections?limit=20&cursor=...`. Only limit/cursor accepted, defaults20/max50; JSON response `{version:1,readAt,collections:[{id,name}],nextCursor}`. Name uses actual CollectionSchema's bounded name rule; no other collection fields. Live page ordered id ASC. No total/count query.
- POST same path with `{ids:[uuid,...]}` (1..50 unique). Response `{version:1,readAt,references:[{id,state:'AVAILABLE',collection:{id,name}} | {id,state:'UNAVAILABLE',collection:null}]}` in exact input order. One output per requested ID, no reason/existence/owner hint. Foreign public/private, deleted and nonexistent all have identical UNAVAILABLE shape and200 outer status. Echo only the caller-supplied normalized ID.

### Custom fields

- GET `/api/v1/search/references/custom-fields?collectionId=<uuid>&limit=20&cursor=...`. Exact keys collectionId/limit/cursor. Response `{version:1,readAt,collection:{id,name},definitions:[{id,collectionId,name,type}],nextCursor}`; metadata only, no options/values. Parent hidden/missing/deleted => generic FILTER_REFERENCE_INVALID422; a real empty owned collection => empty definitions and null cursor. Order definition.id ASC.
- POST same path with `{references:[[collectionId,definitionId],...],detail?:'SUMMARY'|'OPTIONS'}`. SUMMARY default,1..50 unique exact pairs; OPTIONS explicitly1..2 pairs. Wrong collection/foreign parent/deleted/missing definition => UNAVAILABLE with value null, indistinguishable. SUMMARY response `{version:1,readAt,detail:'SUMMARY',references:[{reference:[collectionId,definitionId],state:'AVAILABLE',definition:{id,collectionId,name,type}} | {reference:[...],state:'UNAVAILABLE',definition:null}]}`. OPTIONS response has detail OPTIONS and available definition additionally `options:string[]` in position,id order, at most100 each. Nonselect fields return an actual empty options array; SELECT types require nonempty options under current producer semantics. Unexpected options on nonselect/missing required options/corrupt field shape => invariant failure, not an invented empty list. No partial options list.

The smaller OPTIONS batch is intentional:50 metadata references do not imply permission to return5000 authored options. Two simultaneous definition details cover an active editor and one adjacent prefetch with one/two set SQL statements. Batch limit is declared in schema and tests; exceeding it returns400, not silent first-two truncation. A full50-reference SUMMARY batch remains supported.

### Conditions and category label hydration

- GET `/api/v1/search/references/conditions?categoryId=<uuid>&limit=20&cursor=...`. Exact keys categoryId/limit/cursor. Response `{version:1,readAt,category:{id,key,labels:{de,en}},scheme:null|{id,categoryTemplateId,key,labels:{de,en},active},options:[ConditionOption],nextCursor}`. Include inactive schemes/options. Order option.id ASC for stable ID-only pagination; position remains real metadata and must not be used to resort across pages. Existing category with no scheme => scheme null/options[]/null cursor; missing category => FILTER_REFERENCE_INVALID422. A missing scheme is not a missing category.
- POST same path with `{references:[[categoryId,optionIdOrNull],...]}` (1..50 unique tuples). A null second member explicitly requests category label only; this supports current search-result category labels without a fourth bulk metadata family or50 category detail requests. Response `{version:1,readAt,references:[{reference:[categoryId,optionIdOrNull],state:'AVAILABLE',category:{id,key,labels},scheme:null|{id,categoryTemplateId,key,labels,active},option:ConditionOption|null} | {reference:[...],state:'UNAVAILABLE',category:null,scheme:null,option:null}]}`. Category-only resolution may return scheme summary or null, never all options. Nonnull option requires exact category+scheme relationship; absent/mismatched option yields unavailable, not category data with a fabricated null option. Inactive option/scheme stays AVAILABLE with active false. All labels are current canonical labels, not private item facts.

Each GET is strict raw-query parsing with≤32768 encoded bytes, duplicate/unknown keys and malformed percent/UTF8 rejected. Reuse narrow fixed-key decoding mechanics; `readItemSearchQuery` currently drops arbitrary parent keys in its output, so merely passing allowedKeys `collectionId/categoryId` would not return them. Either factor its raw-key decoding into a small private helper returning the original decoded map while preserving existing search conversion, or add a tiny reference-specific decoder with exactly these fixed fields. Do not send arbitrary keys to the service or widen public search input.

POST reference routes have no query parameters, exact Origin, fresh authentication, application/json,32KiB body and shallow duplicate treatment from§3. GET references require fresh authentication/no-store/requestId, while Origin remains the normal GET behavior (no new GET origin requirement). Endpoint responses return only source-native labels/types/options, never item values, usage counts, notes, certificates, prices or inferred capabilities.

## 7. Correct reference capacity and client consumption obligation

The earlier5A statement implying AST≤50 reference IDs is corrected here. Fifty is a leaf limit. One `in` can contain50 IDs, and multiple such leaves can be valid before16KiB/512-visit structural guards bind. Never cap a valid AST to the first50 references, silently remove values to fit a cache, or run an eager all-tree hydration waterfall. The service's50 batch cap is per request, not a global AST or filter limit.

Required future5C consumption contract (no UI work now):

- Keep complete validated AST and editable draft values separate from disposable label/option caches. Collapsed nodes can render family/operator/selected-value counts while labels are not yet loaded; they must remain editable and lossless. Unknown labels are not invalid references until a current lookup actually returns unavailable.
- Opening one leaf triggers only its own bounded references: collection/category/condition `in` has≤50 values; custom/catalog leaf has one definition. A changed active leaf cancels/invalidates the previous request. Catalog definition metadata/options use the bounded existing-route modes proposed in§7A for the actively edited category/definition; do not fetch every category template in the tree or default100×100 category details.
- A result page has≤50 items. Deduplicate its collection IDs and category/condition pairs and make at most one collection resolve plus one conditions resolve call. Category-only tuples supply labels with no50 calls to getCategoryTemplate. Never call item detail/value endpoints for labels. Hide optional labels until resolved; do not show IDs as required user input.
- Cache proposal: at most150 lightweight reference records/256KiB plus at most2 custom OPTIONS details and one selected catalog definition OPTIONS detail (each guarded by endpoint/contract caps). Category definition-choice metadata has its separate bounded≤100-row projection from§7A; do not cache a default100×100 category detail as though it were a single options list. One open selector page≤50 is separate and replaced rather than appended indefinitely. LRU eviction removes labels only, never AST members or unsaved values. Namespace to current authenticated user, clear on identity change/401/logout; no indefinite local persistence. Broader full-summary expansion may hydrate additional visible rows only on explicit user expansion with≤2 concurrent batch requests and eviction; no automatic fetch-until-all-references loop.
- Relabeling does not change predicate identity. Refresh current visible labels when reopening/explicitly refreshing a query; stale lookup success cannot override a newer token/owner/leaf generation. UNAVAILABLE references get a repairable neutral label; missing or failed label hydration never broadens query execution or disables server authorization. The backend still validates the entire AST independently of what the UI has hydrated.

These bounds preserve valid filters with>50 total reference values and demonstrate why selected-label caching cannot be sized by leaf count alone. A valid nonexistent normalized custom-selection identity stays in the AST/draft as a legitimate no-match operand; absent suggestion membership must neither erase it nor mark the operand invalid. Only a failed definition/owner/type reference has reference-invalid semantics. Root may adjust exact cache sizes in5C after measuring DTO sizes, but must retain separate lossless AST state and finite lazy requests.

## 7A. Actual catalog transfer limitation and smallest finite existing-route delta

Additional inspection requested by root confirms that the existing category detail has **no1MiB response-byte cap** in `catalog-link-routes.ts:run`, and does not read only the selected definition. `getCategoryTemplate` queries up to101 definitions and up to101 options per definition before CategoryTemplateSchema rejects over100. A supported category can therefore have100 definitions×100 options, each with two labels of up to200 UTF16 units plus keys/IDs/positions. That legitimately represents10000 options and can exceed1MiB by several multiples. The101 sentinels bound cardinality and catch malformed excess, but do not make this a small one-definition transfer. No false claim that an existing byte cap rejects it, and no silently truncating it to fit a new cache.

Recommended root decision: add two explicit bounded read modes to the **existing** category detail route, preserving omitted-view behavior and existing callers:

- GET `/api/v1/categories/[categoryId]?view=definitions`: only view accepted; return strict `{version:1,readAt,category:CategorySummary,definitions:[{id,categoryTemplateId,key,type,position,labels}]}`. Complete metadata list≤100 in position,id order,101 sentinel; no options arrays. This supports selecting any real definition without downloading every definition's choices. No cursor needed for this fixed canonical100-definition maximum.
- GET `/api/v1/categories/[categoryId]?view=definition&definitionId=<uuid>`: exact view/definitionId keys; return strict `{version:1,readAt,category:CategorySummary,definition:CatalogAttributeDefinition}` for precisely that category+definition, with≤100 options (101 sentinel) and their exact CatalogAttributeOption keys/labels/positions. Wrong/missing category+definition gives generic FILTER_REFERENCE_INVALID422 under this new mode; default existing full-category mode keeps its old404/error behavior. No selected option input or invented defaults.

Both modes use fresh existing auth/no-store/requestId, strict existing raw-query byte/key syntax and1MiB output cap; fixed source labels/keys only. This is an explicit small extension of the existing canonical read surface, **not a fourth search-reference family** or a new metadata producer. Implement two internal set-read methods (`getCatalogDefinitionChoices(actor,categoryId)` and `getCatalogDefinition(actor,categoryId,definitionId)`) alongside the reference reader and route mode dispatch via a narrow dependency addition. Each has one data statement in the existing bounded read wrapper (3 query calls including settings, plus auth/driver). Metadata-only SQL never joins all option rows; selected-definition SQL restricts exact category+definition before joining≤101 options. Use current canonical definition/option schemas and source labels, not a parallel catalog model. Explicitly detect cap/malformed output; no schema/index/maintenance changes or whole-catalog transfer.

The default category detail and legacy CategoryPicker remain compatible. If root chooses not to include these two modes in5B, record single-definition metadata/options as an open prerequisite and do not claim the full supported-cardinality builder is ready. Future5C cannot resolve the gap by fetching the large default response and cutting it down in the browser. Native proof uses a valid100-definition/100-option category to demonstrate bounded selected-mode transfer and all100 definitions remain chooseable, plus101 sentinels where native constraints permit, exact selected-definition membership, DE/EN labels and unchanged default behavior. This finite delta requires root adjudication before source GO.
