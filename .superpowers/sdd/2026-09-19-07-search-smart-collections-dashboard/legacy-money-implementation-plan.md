**Goal:** Make purchase/custom/catalog raw money safely authorable, explicitly interpretable and consumable by exact Phase07/08 operations while retaining unresolved historical facts and v1 compatibility.

**Architecture:** Add three typed interpretation-event sidecars, personal monetary generations, and one versioned proposal envelope. Preserve existing raw storage and immutable catalog snapshot v1. A single bounded resolver joins the current fact, latest applicable event and direct evidence origin; exact consumers run coverage and evaluation in one authorized database snapshot.

## Review focus

1. A custom MONEY row disappears and returns with the same number: a durable absence token must reject the older write (M2/M3).
2. A catalog operation has byte-identical output: its explicitly submitted money intent must still take effect (M4).
3. A split child survives source erasure or source assertion revocation: it must never become silently independent evidence (M2/M5).
4. Unknown money occurs beyond the page or only under OR/NOT: the whole amount query must reject before matching (M6).
5. A historical code leaves today's currency list, or a queued proposal outlives a parser update: reads and approval preserve the captured facts (M1/M4/M7).

## Decisions recommended for root adoption before M1

These resolve the bounded choices; they are recommendations requiring root adjudication, not reasons to restart design.

**Unit policy v1.** Use `iso4217-2026-09-17:<CODE>` (for example `iso4217-2026-09-17:AFN`) for the 165 numeric-exponent currencies in committed `packages/domain/src/money/currencies.ts`. Keep that artifact immutable under this ID/hash (`33139b438657d1cee116ba737807ea71d19d6de4b90f799a09c56f0cc6a1b0ff`); a future authority update gets a new profile and an explicitly reviewed compatibility mapping, never an implicit alias. Add a small `legacy-money-policy.ts` module consuming this authority; no mutable unit table. New authoring uses its prescribed exponent. Historical classification may declare that exact unit with an independently evidenced exponent0..9: e.g. attested raw123 AFN/exponent0 denotes123 of that unit, while prospective123.00 AFN stores12300/exponent2. Selecting the unit is itself an explicit assertion; the code or current table membership never makes that assertion for an existing fact.

**Unsupported units.** Historical reads accept any `[A-Z]{3}` code. Classification can record evidenced scale0..9 with `unit:{kind:'UNSUPPORTED',label}` (label1..120 NFC characters, no controls); server assigns `unsupported:<assertionUUID>` as its noncomparable unitKey. Such values render exactly, report `UNIT_UNSUPPORTED`, and cannot enter canonical range/totals. No historical currency/redenomination catalogue is invented. Existing retired/N.A. codes such as ANG/BGN/CUC/HRK/SLL/XDR/XSU/ZWL therefore remain UNKNOWN or explicitly known-ineligible until a later evidenced unit policy is approved. Exponents outside0..9 reject with a closed unsupported-interpretation error; raw reads remain possible. This matches the already bounded AST without claiming all bounded exponents have historical evidence.

**Evidence v1.** Historical assertions allow `OWNER_ATTESTATION` for owned purchase/custom, and `OPERATOR_VERIFIED_RECORD` for catalog by persisted MODERATOR/ADMIN. The latter also may be used for personal assertions only by the owner; no administrator bypass of owner access. Each requires a reason1..1000 characters; verified-record also requires a protected opaque reference1..200 characters. References are locators for an existing offline review, not URLs to fetch or claims of machine verification. Owner attestation has optional reference. Store actor and decision timestamp; never manufacture historical author/time. Defer receipt uploads/asset links and bulk classification: they are unnecessary to close this prerequisite and would introduce separate retention/access dependencies. Label the accepted evidence category in private reads and exports.

**Erasure policy v1.** Retain personal audit with the item's existing trash lifecycle; permanent item/definition/account erasure deletes its typed personal events. Retain catalog assertion facts with immutable catalog history, but erase identifying actor/reference/reason metadata on an explicit erasure request. Removing historical evidence retracts its origin; removing only the actor from a server-generated prospective receipt does not invalidate the captured parser contract. Keep machine policy/hash/scale/unit and event IDs for reproducibility. Do not add a timer or promise legal retention periods absent a repository policy. Provide a narrow transactional erasure adapter now; integrate the eventual account-erasure orchestrator later (no such orchestrator exists at BASE). This keeps append-only application behavior from becoming indefinite private-evidence retention.

## Concrete contracts and storage

### Wire schemas (`packages/contracts/src/legacy-money.ts`)

Strict objects only. IDs are canonical UUIDs; integer strings have no sign, leading zeros (except `0`), decimals or exponent notation. Raw bounds0..9007199254740991; event sequences1..9223372036854775807. Mutation body max16KiB; input decimal max80 characters; fact token max2048 ASCII base64url; reference/reason/label reject NUL and control characters. Proposal patch plus envelope retains the existing total65536-byte budget and max100 submitted money paths for a single existing operation.

- `MoneySubject = {family:'PURCHASE',itemId} | {family:'CUSTOM',itemId,fieldDefinitionId} | {family:'CATALOG',entryId,revision,target:{kind:'ENTRY'}|{kind:'VARIANT',variantId},definitionId}`. Never accept an arbitrary table or JSON path.
- `RawMoney = {amountMinor:string,currency:string}`. V1 DTOs continue their existing safe-number shape; v2 wraps the unchanged record and adds this exact interpretation view.
- `MoneyView = {schemaVersion:1,subject,raw:RawMoney|null,factToken,interpretation}`. Interpretation is `MISSING`, `UNKNOWN{reason:NO_EVIDENCE|RAW_WRITER|REVOKED|ORIGIN_ERASED|EVIDENCE_ERASED}`, or `INTERPRETED{exponent,unitKey,basisId,assertionId,eventId,evidenceCategory:null|OWNER_ATTESTATION|OPERATOR_VERIFIED_RECORD,eligibility:ELIGIBLE|UNIT_UNSUPPORTED,decimal}`. `decimal` is exact ungrouped dot notation; public catalog projection excludes factToken, actor, reference, reason and private evidence category. Unknown has no decimal/exponent/unit default.
- `Authoring = {kind:'DECIMAL',profileId:'legacy-money-iso-2026-09-17-v1',currency,decimal} | {kind:'RAW',profileId:same,currency,amountMinor,exponent,unitKey}`. RAW must match the profile's unit/exponent exactly. Decimal grammar is trimmed digits plus optional one comma OR dot and1..exponent fractional digits; no grouping/sign/scientific notation, no fraction for exponent0. Derive with bigint and enforce safe raw bound. Do not call valuation's grouped-locale parser or browser ICU scale helper.
- `NewMoneyIntent = {op:'NEW',authoring}`; `ExistingMoneyIntent = {op:'RETAIN',expectedFactToken} | {op:'CLEAR',expectedFactToken} | {op:'REPLACE',expectedFactToken,authoring}`. Existing MISSING uses REPLACE with its absence token; NEW is only initial item/custom/proposal creation. Omitted money means untouched, never implicit RETAIN/classify. Correction is REPLACE plus required `correctionReason`1..1000, retained as audit metadata; ordinary replacement does not retract earlier assertions.
- `ClassifyMoneyInput = {expectedFactToken,exponent,unit:{kind:'SUPPORTED',unitKey}|{kind:'UNSUPPORTED',label},evidence:{category,reference?,reason}}`; currency comes from raw fact, never a client correction. `RevokeMoneyInput = {assertionId,expectedAssertionToken,reason}`; it can target an older origin, even after raw replacement. Repeating a retraction conflicts; it does not revoke an independent later assertion. Assertion tokens are canonical base64url strict `{v:1,subject,assertionId,evidenceErasedAt:null|ISOtimestamp,revocationId:null|uuid}` (same2048-byte cap), authorized and compared under the origin subject lock. Private classification-history GETs return these tokens for prior assertions, including superseded generations; ordinary item reads need expose only the current effective assertion.
- Server-only `AuthoringReceipt = {schemaVersion:1,profileId,authorityHash,raw,exponent,unitKey,normalizedDecimal}`. Do not persist the original locale text; the exact normalized amount and immutable parser contract prove prospective meaning. Clients cannot submit a receipt as trusted evidence.
- `MoneyFactTokenV1` is canonical base64url JSON of `{v:1,subject,generation:null|uuid,sequence:string,raw:null|RawMoney,effectiveEventId:null|uuid,originId:null|uuid,revocationId:null|uuid}`. Sequence0 means untouched/no events. Tokens are opaque equality preconditions, not credentials; parse strictly, authorize first, compare every field under the fact lock. No secret/signature service is needed. Include effective origin erasure/revocation state so RETAIN cannot ignore changed evidence.

### Additive schema (`packages/db/prisma/schema.prisma` plus one new migration)

Add `CollectibleItem.purchaseMoneyGeneration UUID NULL`, `CustomFieldValue.moneyGeneration UUID NULL`, and `CatalogProposal.moneyInterpretation JSONB NULL`. Migration assigns no historical exponent, generation, event or unit. Null event/generation resolves UNKNOWN for present money and MISSING for absent money.

Create exactly three event tables: `PurchaseMoneyInterpretationEvent`, `CustomMoneyInterpretationEvent`, `CatalogMoneyInterpretationEvent`. Common columns:

| Column | SQL type / invariant |
| --- | --- |
| id | UUID PK, generated server-side |
| sequence | BIGINT positive, serialized under owning subject lock |
| operation | `BASELINE`, `RAW_WRITE`, `CLEAR`, `AUTHOR`, `CLASSIFY`, `COPY`, `REVOKE` |
| rawAmountMinor / rawCurrency | BIGINT/CHAR(3), both present or null;0..9007199254740991 and structural uppercase code |
| exponent / unitKey / unitLabel / basisId | SMALLINT0..9, VARCHAR(128), VARCHAR(120), VARCHAR(80), nullable; AUTHOR/CLASSIFY/COPY require exponent/key/basis and present raw; others carry no asserted scale |
| receipt | JSONB NULL; only AUTHOR, strict AuthoringReceipt validated by service; SQL checks object/version/basic raw equality, never arbitrary user JSON |
| sourceEventId / originEventId / revokedAssertionId | nullable self FKs; COPY requires source+origin at INSERT; REVOKE requires revokedAssertionId at INSERT; only AUTHOR/CLASSIFY can be origins |
| actorId / evidenceCategory / evidenceReference / reason | nullable User FK SET NULL, bounded enum/VARCHAR(200)/VARCHAR(1000); historical CLASSIFY must have category/reason at INSERT; basisId is the exact profileId for AUTHOR, `OWNER_ATTESTATION:v1` or `OPERATOR_VERIFIED_RECORD:v1` for CLASSIFY, and inherited from origin for COPY; raw DB triggers have actor NULL |
| createdAt / evidenceErasedAt | TIMESTAMPTZ default current timestamp / nullable; decision time is createdAt |

Personal identity columns: purchase `(itemId FK CollectibleItem CASCADE,generation UUID)`; custom `(itemId FK CollectibleItem CASCADE,fieldDefinitionId FK CustomFieldDefinition CASCADE,generation UUID)`. No FK to deletable CustomFieldValue. Sequence uniqueness is per durable purchase item or custom item+definition across generations, preventing absence ABA. For present pre-cutover raw money with a NULL stored generation, the resolver uses logical generation all-zero UUID in its token and events; classification does not need to write the raw row or generation column. The resolver normalizes NULL to that sentinel only for an existing present raw fact. Initial missing money keeps generationNULL. The sentinel is never generated for new writes. Index `(subject identity,generation,sequence DESC)`. Current custom absence resolves its latest non-REVOKE CLEAR tombstone; initial absence uses generationNULL/sequence0. To distinguish generation state from the event chosen for interpretation, token.sequence is the latest sequence for the durable personal subject (including historical revocations), while the effective event is the latest non-REVOKE event for the current generation. Raw generation state is never chosen from a later revocation of an older assertion. A later delete/re-add, including identical raw values, cannot recreate that token.

Catalog identity columns: `(entryId,revision)` FK CatalogRevision RESTRICT, `targetKey VARCHAR(36)` equal `entry` or canonical variant UUID, `variantId UUID NULL`, `definitionId` FK CatalogAttributeDefinition RESTRICT; CHECK matches ENTRY/VARIANT target shape. Unique `(entryId,revision,targetKey,definitionId,sequence)`. No FK to ephemeral CatalogAttributeValue IDs or current variant activity. Service/native insert validation resolves this exact path in immutable snapshot, verifies MONEY type/definition/raw equality, and rejects paths absent from that revision.

For each table add indexes on originEventId, revokedAssertionId and actorId. Validate same-family origin/source, exact raw/exponent/unit equality for copies, and same owner+custom definition or same catalog entry as applicable. Flatten COPY origin directly to original AUTHOR/CLASSIFY; maximum read dependency is latest event + one origin + indexed revocation lookup, never recursive lineage. COPY stores its operation actor/time and source/origin IDs, not a duplicate private evidence reference/reason or authoring receipt; evidence is read from the origin. A source copy can be erased without erasing an independently retained origin. Source/origin self FKs use SET NULL on deletion; COPY with a missing origin resolves UNKNOWN/ORIGIN_ERASED and can never be mistaken for an independent assertion. Insert-only origin requirements therefore live in the insertion guard, not a CHECK that would forbid erasure. REVOKE deletion only occurs with complete personal subject erasure; surviving copies lose the origin too. Do not delete selected latest events from a surviving fact and reveal an older interpretation.

SQL guards reject ordinary event UPDATE/DELETE and proposal patch/envelope mutation after submission. Use a content-transition guard, not a GUC, new role, function-caller identity or general trigger bypass. Under every permitted UPDATE, id, subject/generation, sequence, operation, raw pair, exponent/unit/label/basis, receipt, evidenceCategory and createdAt remain `IS NOT DISTINCT FROM` OLD. The only permitted content transitions are:

1. **Evidence erasure:** OLD.evidenceErasedAt is NULL; NEW.evidenceErasedAt equals `transaction_timestamp()`; NEW.actorId, NEW.evidenceReference and NEW.reason are all NULL, with at least one previously non-NULL field removed. References/source/origin links remain unchanged. Once marked, evidenceErasedAt cannot be changed/cleared and erased fields cannot be restored. This transition is available to the already-authorized domain erasure operation; the database constrains its shape, not the end user's authorization.
2. **AUTHOR actor-only removal:** OLD.actorId is non-NULL, NEW.actorId is NULL, and every other field (including receipt/evidenceErasedAt) is unchanged. It preserves the machine receipt. For CLASSIFY actor removal through a User FK action, the BEFORE guard instead normalizes the change into transition1: clears reference/reason and sets evidenceErasedAt to transaction_timestamp(), so an erased historical origin fails closed. COPY actor-only FK removal may retain its independent origin; RAW_WRITE/CLEAR/REVOKE operation-actor FK removal does not erase an origin's evidence. Outside AUTHOR's authorized actor-redaction adapter, these actor-only allowances require that the referenced OLD user no longer exists in the transaction.
3. **Native self-FK removal:** sourceEventId/originEventId/revokedAssertionId may change only from a non-NULL old UUID to NULL after that referenced event no longer exists in the transaction; all remaining fields are unchanged. These self FKs use SET NULL; a surviving COPY with originNULL is UNKNOWN/ORIGIN_ERASED. Direct arbitrary relinking, clearing a live origin, or modifying another column along with FK nulling is rejected. Personal event DELETE is allowed only when its item or custom definition parent no longer exists due to permanent deletion; event DELETE on a surviving subject and catalog event DELETE remain rejected.

A fixed-search_path, no-PUBLIC-execution SQL function may wrap transition1 for consistent statements, using the existing application connection; it creates no authorization boundary or new database/deployment identity. The authorized domain orchestrator owns erasure authorization; database operators remain trusted as elsewhere in the application. Native guards must allow the actual FK SET NULL/cascade order, including combined FK null removals caused by one parent deletion, while enforcing these exact per-column conditions. Historical CLASSIFY origins with evidenceErasedAt resolve UNKNOWN/EVIDENCE_ERASED, including descendants, even before a separately appended REVOKE. AUTHOR actor-only removal retains its valid receipt. Catalog erasure retains immutable raw snapshots and nonidentifying assertion facts.

### Native invalidation, resolver and lock contract

`BEFORE INSERT/UPDATE OF purchaseAmountMinor,purchaseCurrency` rotates purchase generation; `BEFORE INSERT/UPDATE OF moneyAmountMinor,moneyCurrency` rotates custom generation for MONEY. UPDATE OF fires on explicit same-pair writes, not only changed values. Reject direct changes to generation alone; no first-read materialization is necessary because of the logical baseline sentinel. `AFTER` triggers append RAW_WRITE or CLEAR for the new generation. On first mutation of untracked old money, capture a BASELINE unknown event with old raw pair first. Custom DELETE appends a CLEAR tombstone with new generation while item+definition still exist; parent/definition cascade deletion must skip tombstone creation and allow event cascades. Retain deletion history on ordinary set-null only. A failed event insert aborts the raw write. No session variable disables invalidation for v2. Service order is: acquire existing owner/subject locks → read and compare old CAS token → issue raw INSERT/UPDATE → read the actual trigger-assigned generation using SQL RETURNING (or the ORM returned/select field) → append AUTHOR/COPY bound to that returned generation and actual returned raw pair → resolve response → commit. Never preallocate a generation and assume the trigger kept it. Native AFTER-trigger UNKNOWN precedes the service assertion. For bulk custom split inserts, retrieve each child item+definition generation after insertion inside the same transaction before appending COPY. Unrelated ORM updates must omit monetary column names entirely; a title-only UPDATE that unnecessarily includes unchanged raw columns intentionally invalidates meaning.

Resolve latest non-REVOKE event matching current generation and exact raw pair (catalog exact immutable identity). No event => UNKNOWN; event/raw mismatch => closed MONEY_DATA_INTEGRITY error. A latest AUTHOR/CLASSIFY is its own origin; COPY checks direct origin, erased state and any REVOKE targeting it. Independent CLASSIFY supplies a fresh origin. Raw replacement does not insert REVOKE. Display and coverage use this resolver exclusively.

Locks follow actual code: item create locks owned collection; update locks owned live item; custom mutation locks item then definition; split discovers catalog refs, locks catalog entry/variant SHARE via `item-catalog-locks.ts`, then item, then existing sorted asset locks. Add monetary work inside these transactions, never an item→catalog lock. Catalog approval retains persisted authority → proposal row → entry row; mutation/classification/rollback serialize on entry. Personal native triggers serialize sequence allocation on the owning item row, including direct raw writes. Custom direct SQL can deadlock if it first locks the value row while a service holds the item; PostgreSQL abort/retry is acceptable, but partial data or attaching metadata to the winner is not. Add a bounded closed conflict/dependency mapping, no indefinite retries.

Revocation does not lock every dependent copy. It locks its own origin subject and appends REVOKE; copies always rejoin that origin. A copy created concurrently either reads before revocation and becomes UNKNOWN on the next read, or reads afterward and copies UNKNOWN. Do not acquire another item's lock while holding the current item simply to traverse lineage. Coverage/report read transaction is RepeatableRead and pins the observed revocation state; returned facts make no stronger later-time claim.

### Catalog proposal envelope and path mapping

Public v2 submit endpoint receives `{proposal:<existing submit input>,money:{schemaVersion:1,intents:[{target:'ENTRY'|'OPERATION_VARIANT',definitionId,intent}]}}`. Existing UPDATE_VARIANT's UUID is already in `proposal.patch`; ADD_VARIANT gets its UUID on approval and uses OPERATION_VARIANT until then. CREATE_ENTRY cannot contain variants in existing contract. Avoid client-provided generated UUIDs or array-index paths. Require exactly one intent for every submitted MONEY attribute and none for nonmoney/untouched paths; max100, unique target+definition. For base-existing fields allow RETAIN/REPLACE; newly added fields use NEW; omission from replacement arrays removes the field. No CLEAR element with a raw attribute still present.

At submission server derives raw values from authoring, requires equality with corresponding raw patch value, validates RETAIN against exact base revision/path/token/raw, then persists `moneyInterpretation={schemaVersion:1,baseRevision,patchDigest,paths:[{target,definitionId,kind:'AUTHORED',receipt}|{target,definitionId,kind:'RETAIN',factToken}]}`. Digest is SHA256 of existing canonical patch serialization and additionally checked against stored patch; no signature over untrusted client receipts. Approval reparses bounded stored envelope, verifies digest/paths, resolves generated variant target, and checks RETAIN token again under entry lock. A changed interpretation without a raw revision change is a proposal conflict, not silently refreshed evidence. A profile retired for new authoring remains readable for queued receipts; an unknown profile/hash is unavailable/conflict, never reparsed with today's authority. Null legacy envelope marks only submitted MONEY paths UNKNOWN; untouched paths still carry. No external fetch at submit/approve. Carry-forward may cover up to10100 snapshot paths (100 entry attributes plus100 variants×100 attributes) even though one operation submits at most100 intents; use bounded batch reads/inserts (chunks≤500), never one query per path or an accidental100-path truncation.
