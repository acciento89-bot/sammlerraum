## Smallest executable Task1/2 contract

### Envelope, parser and budgets

Proposed request: `SearchItemsInput = { text?: string, filter?: { version: 1, root: ItemFilter }, lifecycle?: 'ACTIVE'|'ARCHIVED'|'DISPOSED'|'ALL', limit?: number, cursor?: string }`. Actor is server-authenticated and not part of input. Default lifecycle ACTIVE; ALL includes archived/disposed but never deleted item/collection. ARCHIVED/DISPOSED predicates use actual timestamps; where both are present, DISPOSED takes precedence. Root null/omitted means no filter. `OWNED` is server-fixed scope, not an unchecked owner ID.

Recommended finite bounds to settle once in Task1: raw decoded filter JSON<=16KiB; encoded whole query<=32KiB; smart mutation body<=24KiB; text<=200 Unicode code points and <=800 UTF8 bytes; cursor<=2048 ASCII base64url chars; page default20/max50; response<=1MiB. Accept no unknown/duplicate query keys. Routes read bytes with an actual streaming ceiling and fatal UTF8 handling; Content-Length alone is not protection. Check raw URL bytes before `URLSearchParams`/JSON parsing. A lexical bracket/string-aware nesting precheck (max32 JSON containers) precedes JSON.parse; it is a size/depth guard, not a second JSON grammar. Syntax remains JSON.parse's job.

Then an iterative structural check before recursive schema validation: <=512 visited containers/properties-budgeted nodes, logical depth<=5, leaf count<=50, and/or children1..50, not exactly one child, set values1..50, strict per-node keys, finite strings as above. A raw object passed directly to domain code receives the same iterative bounds and cycle rejection, not only an HTTP byte cap. Reject empty AND/OR and malformed/not-extra-children nodes. This protects recursion and width before Zod descent. Canonicalize UUID case and established tag/value rules; stable property serialization for cursor context is deterministic, not user-authored SQL.

Use closed discriminated unions and fixed operator sets; no client-chosen column/path, raw regex, JS expression, SQL fragment or generic Prisma object. Invalid input gets stable 400 `FILTER_INVALID`; budget violation 400 `FILTER_TOO_COMPLEX`; unsupported or unsafe operation 422 `FILTER_UNAVAILABLE` with a safe reason. A foreign collection/custom-definition selector produces the same generic error as a missing one, without echoing private metadata. An unavailable leaf causes the **entire** query to fail even inside OR/NOT; it is never compiled as false/true and never silently omitted.

### Authorization, counts and cursor

One narrow `buildOwnedItemPredicate(actor, validatedQuery, resolvedDefinitions)` produces the predicate used inside both rows and totals; dashboard consumes the same scope semantics. It accepts only validated internal discriminants and emits bound Prisma predicates or fixed typed SQL fragments. Keep this internal to search/dashboard, not a generic query engine.

Authenticated principal derives from the established fresh session boundary. Every query requires item owner and collection owner to equal actor; collection and item not deleted. Owner access works for PRIVATE/UNLISTED/PUBLIC. A foreign PUBLIC item is outside OWNED, just as a foreign private one is. No claim that owner-only counts cover public discovery. Returned summary is a dedicated compact whitelist (ID/title/collection/category/condition/quantity/lifecycle/trade/visibility setting/created/updated and bounded thumbnail reference as authorized), not `item.*` or private notes/documents/storage facts.

Initial sort: `createdAt DESC, id DESC`, immutable createdAt tie-breaker. Cursor payload `{v:1, contextHash, after:{createdAt,id}}`, canonical base64url UTF8, bounded/strictly decoded. Hash includes operation kind, actor ID, normalized text+versioned filter, lifecycle, sort and page size; for saved resolution include smart ID+revision. Revalidate actor/predicate on every page: a cursor is not a permission token. A signed token is optional if later opacity/tamper protection is required; a scope hash alone is not cryptographic authorization. Reject cross-actor/query/smart-revision/sort replay. Changed permissions/lifecycle apply on every request.

Return `{items, total, nextCursor, scope:'OWNED', readAt}`. `total` counts the entire authorized filter before cursor, not current page or all inventory. Use one SQL statement or bounded RepeatableRead transaction for rows+count+metadata so a single response is consistent; no cross-request snapshot promise. If total exceeds safe JSON number range, fail explicitly or specify decimal-string count in Task1; do not silently round. Page continuation requests use live keysets, so concurrent insertions do not imply a frozen catalogue. Root should prefer the established domain JSON conventions for final field names rather than duplicate equivalent pagination frameworks.

## Task4: dashboard and the load-bearing legacy MONEY gate

### Smallest truthful legacy contract

Root L1 is binding. Existing legacy purchase/custom/catalog money stores a safe integer and currency without exponent or interpretation provenance. The recorded runtime and pinned ISO maps differ for sixteen currencies; runtime also accepts retired/undefined-unit codes absent from the new numeric list. A current map agreement for one currency is not historical provenance. No runtime probe, fresh deployment assumption, automatic exponent backfill, integer rescale, or global helper replacement is authorized here.

Recommended initial wire shape:

```ts
type PurchaseTotals =
  | { status: 'EMPTY'; groups: []; pricedItemCount: 0; missingItemCount: number }
  | { status: 'UNAVAILABLE'; reason: 'LEGACY_MONEY_UNCLASSIFIED';
      groups: null; pricedItemCount: number; missingItemCount: number;
      unclassifiedItemCount: number };
```

Every non-null legacy purchase pair counts as unclassified until an approved evidence-backed classification exists. Count only owned selected items. An actual stored zero is priced/unclassified, not missing. `EMPTY` is valid only for a selected scope with no stored prices; it means no price data, not zero purchase cost. No raw integer sum is shown as money, and unavailable is not represented by `[]`, `0`, or silently dropping sixteen suspect currencies. Missing-data counts may show the scope's gaps without disclosing another owner's records.

Once a separately approved classification producer exists, extend this discriminated contract with `AVAILABLE` or `PARTIAL`, grouping `(currency, storedExponent, interpretationProvenance)` and reporting unclassified/missing coverage separately. Every partial total must say it is partial; do not call a classified subset the full purchase cost. Existing safe-number writes/read shapes remain unchanged until the scoped producer design explicitly changes them. Presence filters remain usable now; all canonical legacy-money ranges fail as a whole. A low-level raw-unit operator is not proposed for product UI because users would mistake it for a currency range.

Smallest later remediation alternatives for root to choose in a separate design:

1. **Proved-empty first deployment plus coordinated prospective writes.** Operator proves the intended database has no affected purchase/custom/catalog MONEY values, records the evidence/cutover, and upgrades every real producer (UI/API/import/catalog snapshots) to store source interpretation metadata atomically with new amounts. Empty local fixtures or an unmerged branch do not prove production emptiness. An empty database alone does not fix future unversioned writers. Do not silently classify rows arriving during a non-atomic cutover.
2. **Existing data.** Add nullable stored exponent/interpretation provenance plus explicit classification status (precise columns/table shape needs producer-specific design). Every pre-existing legacy record remains explicitly `UNKNOWN`, with exponent/provenance null; this classification says that evidence is absent, never infers scale. New or explicitly replaced monetary writes capture the **actual parser/display interpretation** and its stored exponent atomically, for example a reviewed `LEGACY_ICU_V1` path versus a deliberate `ISO_PINNED_V1` path. Pin that parser's interpretation instead of asking a later runtime's ICU to rediscover it. The browser may not self-certify arbitrary metadata: the server validates an allowed writer contract and derives/verifies its exponent. Raw-integer API/import clients that cannot attest interpretation remain unknown, or use a separately versioned explicit amount contract; silently assigning today's ISO to those clients is forbidden. Merely editing a title must never classify an old price. A scoped operator/owner review records evidence and chosen interpretation for old facts, retains original raw integer/currency, logs who classified and why, and corrects amounts only through a separate explicit correction workflow. Classification may attest historical ICU-based meaning rather than rewrite as current ISO. Native constraints, updates, imports, catalog revision history and retained historical pairs must agree. Unknown/retired/undefined-unit currencies stay readable but outside canonical aggregation until deliberately handled.

Both alternatives require dry-run inventory, historical/runtime evidence or owner attestation, concurrent writer/cutover strategy, preservation of raw facts and rollback/audit policy before any migration/backfill. This preparation does not perform an inventory of real data. Phase08 must carry the restriction: raw legacy export may preserve raw integer/currency with explicit interpretation unknown; it must not label that as a known decimal amount or use it for a canonical insurance valuation. Phase13 must resolve or explicitly restrict those operations. This is a prerequisite, not cosmetic deferred UI work.

The additive alternative's minimum cost is metadata at each actual purchase/custom/catalog producer and historical snapshot boundary, updated validated writer contracts, exact stored-exponent reads, and an explicit classification workflow; it is not a single universal display-helper replacement. Until those producers exist, Phase07 has no `AVAILABLE` legacy totals. Afterwards a money-range response must either reject incomplete scope or explicitly return matched known items **plus unknown coverage** under a declared partial-result contract. Unknown prices do not become non-matches. Dashboard partial totals must expose unclassified item/unit counts and cannot be labelled complete canonical costs. Prefer rejecting incomplete range operations initially because partial matching complicates NOT/OR and saved-query semantics; root can approve a separate three-state matching design later if product needs it. No metadata migration implementation or classification of real records is authorized by this alternative.

### Available dashboard metrics

`getDashboard(actor, scope)` receives the same validated filter+lifecycle as search, default current ACTIVE holdings. Serve authenticated GET `/api/v1/dashboard` with bounded query and no-store; Task4 must add its route/dependency adapters and export contracts, despite the plan's abbreviated file list.

Use explicit `itemCount` (rows), `unitCount` (sum quantity, exact decimal string if needed), physical owned `collectionCount` and filtered `matchedCollectionCount` separately.
