## Proposed outcome and bounded decisions

Use additive interpretation records plus versioned prospective writers, with explicit owner/operator classification of historical facts. This makes purchase ranges/totals and canonical Phase08 monetary reports attainable for evidenced scopes, without permanently removing those features or pretending all historical records can be resolved. Unknown scopes remain visibly blocked. A useful legacy/raw export remains possible with explicit UNKNOWN metadata and no invented decimal amount.

The smallest coherent scope covers **all three actual money families**, their clone/history paths, and compatibility clients. Fixing only purchase input leaves catalog/custom amounts and split/rollback/proposal seams unsafe. Do not turn this into a general accounting, FX, valuation, payment or event-sourcing subsystem.

## Minimal identities and additive persistence

Keep `purchaseAmountMinor/purchaseCurrency`, native custom columns, current catalog JSON, every old proposal patch and every `CatalogRevision.snapshot` unchanged. Migration inserts no claimed exponents and does not enumerate real records to classify them. A non-null raw value with no valid matching event is explicitly UNKNOWN in the new read contract. Null pair/absent field is MISSING, a different state; zero is present and still unknown without evidence.

Proposed schema shape (design, not migration SQL):

* Purchase: add nullable `purchaseMoneyGeneration` UUID on the item; absence denotes the untouched pre-cutover generation. Typed `PurchaseMoneyInterpretationEvent` has item FK, generation key, sequence, raw amount/currency, state, exponent/basis/provenance fields, actor/time/reason/evidence reference and optional source-event reference.
* Custom: add nullable `moneyGeneration` UUID on the value; `CustomMoneyInterpretationEvent` references durable item+field-definition identities, **not the deletable value row**, with generation and the same narrow payload. Explicit removal/re-add gets a new generation. Event FK/deletion retention must not prevent legitimate value removal.
* Catalog: `CatalogMoneyInterpretationEvent` references `(entryId,revision)` plus target kind ENTRY/VARIANT, variant UUID when relevant, definition UUID, raw pair and sequence. A check makes target shape consistent. Service validates the exact MONEY path in the immutable snapshot, including type/definition and raw equality; an arbitrary client JSON path is forbidden. Link to prior event only when explicitly carried/restored. No new generation UUID is needed here: immutable revision+target+definition already identifies the fact.
* Proposal: one nullable **versioned validated interpretation envelope** alongside existing `patch`, containing only submitted money paths and parser receipts or explicit retain instructions bound to base revision. Old null envelope means UNKNOWN. Its immutability follows the submitted patch, while decision status remains mutable. The proposal is not itself canonical catalog history.

Each event is append-only; one ordered sequence per fact/version makes supersession explicit. Initial untouched history need not get millions of artificial UNKNOWN audit rows. Resolve absence as UNKNOWN; on first mutation/classification materialize a fact token under the existing item lock and compare expected raw pair plus absence token. On subsequent changes use the generation and last event sequence for CAS. Store actual raw pair in events as well as reference identity: correction must retain what was corrected, and a digest alone cannot reconstruct the previous number. No amounts enter generic logs.

Why these identities are necessary: `(itemId,rawPair)` alone has an ABA hole (A→B→A) and cannot distinguish same-number replacement; custom values can be deleted/reinserted; catalog current rows are deleted/recreated on unrelated changes. `updatedAt` is not a money generation and changes on unrelated edits. Event sequence distinguishes two conflicting classifications of unchanged raw data. A generation is not a new classification: its event may remain UNKNOWN or point to explicitly preserved evidence.

Native constraints enforce amount bounds, upper-case raw currency shape, status/exponent pairing and finite exponent range (recommend0..9 for the additive interpretation contract, subject to evidenced legacy requirements). Known requires exponent, basis, unit identity, provenance and valid target; UNKNOWN requires no asserted exponent. Reject unsupported evidenced exponents rather than clamp them. New writers stay within the existing safe-number raw storage bound. Amount products/sums use arbitrary precision and wire strings; do not widen legacy JSON numbers as part of this change.

Prefer three typed tables over a polymorphic universal money registry: actual FKs and family-specific authorization are easier to inspect. A shared code validator is sufficient. No separate materialized sum table or global event bus is needed. Native triggers on personal monetary column writes must invalidate the previous generation, including explicit same-pair writes; service writes install the new event in that same transaction. This provides a fail-closed boundary for overlooked/older writers. Classification-only operations do not update raw columns. Arbitrary DDL/disabled-trigger operators remain outside application guarantees, as with catalog history today.

### Compared with versioned snapshots

A `CatalogSnapshotV2` embedding `{raw,exponent,provenance}` makes newly authored history self-contained, but requires dual readers in current/history/proposal/rollback/market snapshot consumers and a v1 projection for existing clients. It still needs an external append-only classification/correction record for old immutable snapshots: putting assertions only in new revisions cannot describe the actual old revision. It therefore adds a second representation without removing the historical sidecar need. Recommended first step is v1 raw snapshots + versioned external interpretation envelope. Cost: consumers must join/pin event sequence, and a raw snapshot alone is not a canonical monetary export. Revisit embedded v2 only if an offline self-contained catalog artifact is a real requirement.

## Prospective contracts capture what actually parsed the amount

Introduce an explicit v2 money mutation/read capability (separate v2 endpoints/envelopes, not unknown keys appended to strict v1 JSON). Keep the v1 numbers/pairs intact. V2 read wraps the unchanged raw record with interpretation state, exponent, human-readable basis and opaque fact/version token. V1 reads remain available and must never be used internally as evidence for canonical totals.

Concrete proposed seams: v2 item create/update accepts purchase intent while reusing existing core item service; v2 custom-field set accepts per-field intent; v2 proposal submission carries the separate money envelope. Owner interpretation reads/classification/revocation are narrow item purchase or item+field routes; catalog equivalents are entry+revision+typed target+definition routes with persisted moderator authority. Do not expose arbitrary subject-table names or JSON paths. Exact route spelling can follow repository conventions, but a single generic item PATCH cannot cover custom values or immutable catalog facts.

Minimal wire discriminants (illustrative names; root can freeze them in the contracts brief):

```ts
type Interpretation =
  | { state: 'MISSING'; factToken: string }
  | { state: 'UNKNOWN'; factToken: string; reason: 'NO_EVIDENCE'|'RAW_WRITER'|'REVOKED' }
  | { state: 'INTERPRETED'; factToken: string; exponent: number;
      basisId: string; unitDefinitionId: string;
      eligibility: 'ELIGIBLE'|'UNIT_UNSUPPORTED'; assertionId: string };
type MoneyIntent =
  | { op: 'RETAIN'; expectedFactToken: string }
  | { op: 'CLEAR'; expectedFactToken: string }
  | { op: 'REPLACE'; expectedFactToken: string;
      authoredDecimal: string; currency: string; parserProfileId: string };
```

Create has a separate explicit NEW branch without an existing-fact token; existing-fact replacement must never accept an omitted token. New raw integer v2 clients use a separate strict variant with exact integer string and registered explicit exponent/unit contract, not both integer and decimal optional fields. Raw v1 output remains safe-number JSON; v2 may wrap the same raw pair rather than changing its type. Use bounded bodies/evidence strings and existing origin/session protections. Integrity violations (event/raw mismatch or impossible typed target) are explicit data errors, never a fallback interpreted amount. Retry of a timed-out mutation requires a fresh read; the first version need not add an idempotency subsystem. CAS makes replay with an old token conflict, but UI must not claim that every unknown network result was a failed write.

New UI sends an authored amount string, currency, input grammar/profile ID and intent (`REPLACE`, `CLEAR`, or explicit `RETAIN` token). Server selects an allowlisted immutable parser profile and derives the raw integer and exponent; it never trusts a client `known:true`, claimed ICU version or arbitrary exponent. It returns the normalized exact major amount for acknowledgment. Display uses that stored exponent exactly, with Intl only for separators/symbol presentation. Client previews use the same versioned data/profile, and a mismatch gets an explicit refresh/review error rather than silent correction.

The first profile may freeze the reviewed current legacy helper behavior (comma-or-dot/no-grouping, its exact future currency/exponent table) under a named version. Record profile ID/hash, stored exponent and display basis. **Do not call it historical ICU evidence**: it establishes the submitted future contract. Browser ICU lookup cannot be the ongoing scale authority, since different devices can differ. If keeping runtime-specific parsing temporarily, send original decimal text plus exponent and server must validate a registered actual profile and exact round-trip; unregistered client/runtime interpretation stays UNKNOWN. Prefer the frozen profile to avoid that extra path.

An optional deliberate ISO-pinned profile has its own ID and reviewed currency-unit mapping; UI clearly shows its resulting amount before replacement. No universal helper swap, silent conversion on language change, or automatic reinterpretation of an existing field. Raw API clients can instead use a v2 explicit amount/exponent contract tied to an allowlisted unit/profile; server checks bounds and profile consistency. This is a new contractual declaration of meaning, not proof that an old raw number meant the same thing.

## Classification is an explicit evidence operation; correction is separate

A bounded owner review lists their raw facts and clearly labels interpretation missing. It may show the existing display as **legacy display, unverified**, not as a preselected truth. The actor chooses a supported interpretation only with evidence: original receipt/text amount and unit, a demonstrably versioned producer record, or explicit owner attestation of what was intended. Operator classification of catalog history needs persisted authority and provenance; ordinary user proposals remain subject to moderation. A runtime executable/hash can corroborate parser behavior but cannot prove that a particular row came from it without a binding record.

Classification request identifies exact fact/generation or immutable revision/path, expected event sequence, proposed exponent + unit identity + basis, and evidence category/reference/reason. Server locks, rechecks ownership/authority and equality, validates the interpretation, and appends a CLASSIFY event. Raw value/currency do not change. It records actor and decision time distinctly from unknown historical author/time; no invented historical timestamps. Batch classification is a separately scoped operator action with a frozen explicit target manifest and preview, not `UPDATE all rows for currency`. This preparation does not authorize that action or inspect real data.

If evidence says the **number or currency is wrong**, classification cannot repair it. Use explicit CORRECT/REPLACE with before/after raw facts, a reviewed new writer receipt and reason. Preserve the old event/raw value; personal current value changes, catalog gets its normal new canonical revision when raw changes. If only a previous interpretation assertion was wrong, supersede/revoke that assertion on the same immutable raw fact; keep both assertions and do not rewrite snapshots. Revocation returns it to UNKNOWN when no defensible replacement exists. No broad conversion job is proposed.

Inherited copies need an explicit evidence-origin reference as well as the immediate split/revision source reference. A later **retraction of that interpretation assertion** makes dependent copies ineligible/UNKNOWN on current reads, until independently classified; no amount changes automatically. Store an explicit retracted-assertion reference so this check is an indexed join to the origin, not recursive unbounded lineage traversal. An ordinary correction/replacement of the source's current raw amount does not retract its older assertion or mutate a split child's fact. A new independent classification becomes a new origin. Reports pin the as-of assertion and revocation state; past generated bytes remain historical evidence of what was reported, not a claim that a subsequently retracted assertion is still valid.

Raw codes remain readable independent of today's numeric ISO list. L1 specifically records ANG/BGN/CUC/HRK/SLL/XDR/XSU/ZWL mismatch cases and XDR/XSU N.A. units. Neither default exponent2 nor the ISO valuation validator may be applied to historical reads. Split historical-read validation from new-writer validation: existing uppercase raw codes and safe integers must survive current/future currency-list changes, including old catalog snapshot parsing. A frozen legacy-read acceptance set or structurally validated historical raw-code schema can preserve this; do not narrow it to the new valuation currencies.

If the current presentation runtime cannot format a retained historical code, show its raw integer/code with the unverified-interpretation label (or known exact decimal/code when a stored exponent exists), rather than failing the whole item/snapshot read. This fallback is presentation preservation, not an inferred exponent. Shared snapshot validators used for market mapping must likewise accept historical raw facts without making them monetary inputs to that separate system.

Exponent alone establishes a decimal scale, not a meaningful monetary unit or comparability. Record a small versioned unit-definition reference for eligible interpretations (including any evidenced historical currency definition). N.A./unsupported unit interpretations remain readable but ineligible for canonical totals/ranges until an explicit supported unit meaning is established. Do not substitute a successor currency, convert redenominations, apply FX, or combine same-letter codes whose unit identities differ. Captured legacy ICU exponent0 for AFN may be a valid attested legacy meaning; it is not silently changed to current ISO exponent2. These values can be displayed exactly from their stored exponent and retain their provenance.

## Concurrency, coherent reads, rollback and privacy

Use existing collection/item and catalog entry/proposal locks in their established order. Add money CAS under those locks; competing replace/classify/split/clear must have one winner or a stale-fact conflict, not last-writer metadata attached to another amount. All raw write, generation change, event append and proposal/revision linkage commit together. Native personal invalidation is triggered on explicit monetary writes, including same-pair SQL updates. If an event insert fails the entire monetary write rolls back. Classification CAS also checks last event sequence. A same-raw replacement cannot fool it. Catalog classification, mutation and rollback serialize on the entry; proposal approval retains its proposal→entry lock order. A classification service must not invert it.

Coverage checks and result rows/totals run in one statement or bounded RepeatableRead snapshot. Otherwise an unknown check can pass before a concurrent replacement makes the fetched amount unknown. Paged responses remain live, and repeat coverage validation on each request. Monetary sorts/cursors bind query/actor/unit/interpretation semantics; do not imply a frozen inventory across pages. Report jobs must materialize a consistent authorized selection of raw values, quantities and interpretation event IDs in one bounded snapshot (or explicitly staged snapshot design for large jobs), then render those frozen facts. A source revision is not enough to reproduce a report if later interpretation events change.

Roll out additively: schema/readers with UNKNOWN default; upgraded writer adapters plus invalidation; coordinated writer cutover; UI; classification tools; then canonical consumers. Existing data is never automatically given exponent metadata. Drain old in-flight catalog writers/proposal approvals during activation; old code can bypass receipt propagation or return raw no-ops. Unknown new revisions are fail-closed, but this is not an excuse to skip deployment coordination. New client capability negotiation must prevent sending v2 intent to an old server that might strip unknown keys. Migration itself is not authorization to classify.

Application rollback keeps additive schema/event data. Disable canonical monetary consumer/writer capabilities before rolling back to a version that does not understand events; legacy reads/raw writes may continue, with native invalidation and later UNKNOWN reconciliation. Do not down-migrate/drop event tables to make old binaries happy, roll raw integers back from exponents, or delete audit on rollback. Recovery can re-enable after proving every actual writer is upgraded. A dry-run operational inventory at that future time must count purchases, custom values, current/historical catalog MONEY paths and pending proposals; it must not emit personal amounts/evidence in shared logs. Local emptiness is irrelevant to the present design.

Purchase/custom amounts, evidence and audit follow owner-only access and no-store reads. Hidden/foreign IDs return the established hidden outcome; coverage, filters, counts and errors must not reveal foreign money. Global catalog public amount interpretation may expose a safe status/exponent/basis projection, but actor identity, private receipts and evidence attachments are separately restricted. Do not put confidential evidence into already-public catalog source text. Reuse authorized document references only after verifying object ownership/access; no automatic evidence download/public link. Audit retention/deletion must be specified for account erasure and catalog governance before implementation: append-only application semantics do not mean indefinite public retention. Prefer bounded evidence metadata and protected references, not copying receipt contents into every event.

## Phase07 complete coverage and exact semantics

Define the authorized candidate set **before monetary AST evaluation**: owner/live-parent/lifecycle plus independently specified outer scope such as collection and text. For every distinct money leaf, inspect every candidate's referenced actual field (purchase, selected custom definition, catalog ENTRY or exact SELECTED_VARIANT). Missing target/link/field is MISSING; do not inspect other variants. Use an independent collection/category/field selector only where its meaning is fixed outside the AST. Do not obtain the coverage set by deleting monetary clauses from an arbitrary Boolean tree: removing a clause under NOT/OR can shrink the candidate universe incorrectly.

If any present referenced value is UNKNOWN, revoked, malformed or lacks eligible unit meaning, return a whole-query `MONEY_INTERPRETATION_INCOMPLETE` with safe actor-scoped coverage and **no matched rows, total or next cursor**. Apply the same rule under `NOT`, `OR`, nested trees, sort, saved-query creation/resolution and dashboard filter. Counts cover the entire candidate scope, not the first page. For simplicity this conservative rule may reject unknown values of another currency too; optimize only with a proved semantics-preserving rule later. No `COALESCE(unknown,false)`, partial-match toggle or silently omitted clause.

Once all relevant present facts are eligible, positive range/equality predicates on missing or other-unit values are false; NOT complements those results exactly as preflight defines. `present`/`missing` and explicit interpretation-status filters do not require an amount comparison and can help users find unresolved values. Save schema/version and unit/profile semantics, not matched IDs. Revalidate coverage on every Smart Collection resolution: a later raw client write can make a previously usable saved range unavailable. Do not silently edit the saved query.

Range bounds are exact integer strings with bound exponent and unit identity. For compatible known values, compare `valueInteger * 10^boundExponent` with `boundInteger * 10^storedExponent` using exact integer/NUMERIC arithmetic. This handles different stored exponents without changing stored raw facts. Do not use JS Number, locale-formatted text, rounded decimal or float SQL. Currency alone is insufficient for cross-unit comparison. Monetary sorting is within one explicit comparable unit, with exact normalized comparison and deterministic item-ID tie-breaker; no global multicurrency ordering.

Purchase total means **current selected quantity × known per-unit purchase**, not lifetime spend. Group by currency + stored exponent + unit definition; provenance coverage can be reported separately and must remain traceable. Do not sum custom/catalog MONEY as purchase cost: those definitions do not establish a per-unit cost basis. No FX or valuation fallback. Use arbitrary-precision arithmetic because quantity multiplication/sums can exceed bigint even though each legacy integer is safe.

For each family return complete item/unit coverage: `selected = missing + present`, and `present = interpretedEligible + unknown + knownIneligible`. These latter buckets are disjoint; integrity-error counts, if returned instead of a hard data-error response, must form an additional explicit bucket. For catalog include path count where multiple requested definitions exist; item counts alone must not hide several unresolved attributes. Actual zero is covered when interpreted, unknown when not, never missing. No rows is EMPTY; all prices missing means NO_PRICES; unknown/ineligible means UNAVAILABLE and canonical total `null`; known prices plus missing ones may show an explicitly labelled known-price subtotal with missing coverage, never a complete inventory purchase cost. A complete canonical cost requires no unknown/ineligible **and no missing prices** in its promised scope. Optional known subtotals during unavailable state are unnecessary for the smallest implementation; omit them initially.
