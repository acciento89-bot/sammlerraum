## Decisions recommended for root adoption before M1

These resolve the bounded choices; they are recommendations requiring root adjudication, not reasons to restart design.

**Unit policy v1.** Use `iso4217-2026-09-17:<CODE>` (for example `iso4217-2026-09-17:AFN`) for the 165 numeric-exponent currencies in committed `packages/domain/src/money/currencies.ts`. Keep that artifact immutable under this ID/hash (`33139b438657d1cee116ba737807ea71d19d6de4b90f799a09c56f0cc6a1b0ff`); a future authority update gets a new profile and an explicitly reviewed compatibility mapping, never an implicit alias. Add a small `legacy-money-policy.ts` module consuming this authority; no mutable unit table. New authoring uses its prescribed exponent. Historical classification may declare that exact unit with an independently evidenced exponent0..9: e.g. attested raw123 AFN/exponent0 denotes123 of that unit, while prospective123.00 AFN stores12300/exponent2. Selecting the unit is itself an explicit assertion; the code or current table membership never makes that assertion for an existing fact.

**Unsupported units.** Historical reads accept any `[A-Z]{3}` code. Classification can record evidenced scale0..9 with `unit:{kind:'UNSUPPORTED',label}` (label1..120 NFC characters, no controls); server assigns `unsupported:<assertionUUID>` as its noncomparable unitKey. Such values render exactly, report `UNIT_UNSUPPORTED`, and cannot enter canonical range/totals. No historical currency/redenomination catalogue is invented. Existing retired/N.A. codes such as ANG/BGN/CUC/HRK/SLL/XDR/XSU/ZWL therefore remain UNKNOWN or explicitly known-ineligible until a later evidenced unit policy is approved. Exponents outside0..9 reject with a closed unsupported-interpretation error; raw reads remain possible. This matches the already bounded AST without claiming all bounded exponents have historical evidence.

**Evidence v1.** Historical assertions allow `OWNER_ATTESTATION` for owned purchase/custom, and `OPERATOR_VERIFIED_RECORD` for catalog by persisted MODERATOR/ADMIN. The latter also may be used for personal assertions only by the owner; no administrator bypass of owner access. Each requires a reason1..1000 characters; verified-record also requires a protected opaque reference1..200 characters. References are locators for an existing offline review, not URLs to fetch or claims of machine verification. Owner attestation has optional reference. Store actor and decision timestamp; never manufacture historical author/time. Defer receipt uploads/asset links and bulk classification: they are unnecessary to close this prerequisite and would introduce separate retention/access dependencies. Label the accepted evidence category in private reads and exports.

**Erasure policy v1.** Retain personal audit with the item's existing trash lifecycle; permanent item/definition/account erasure deletes its typed personal events. Retain catalog assertion facts with immutable catalog history, but erase identifying actor/reference/reason metadata on an explicit erasure request. Removing historical evidence retracts its origin; removing only the actor from a server-generated prospective receipt does not invalidate the captured parser contract. Keep machine policy/hash/scale/unit and event IDs for reproducibility. Do not add a timer or promise legal retention periods absent a repository policy. Provide a narrow transactional erasure adapter now; integrate the eventual account-erasure orchestrator later (no such orchestrator exists at BASE). This keeps append-only application behavior from becoming indefinite private-evidence retention.

### Wire schemas (`packages/contracts/src/legacy-money.ts`)

Strict objects only. IDs are canonical UUIDs; integer strings have no sign, leading zeros (except `0`), decimals or exponent notation. Raw bounds0..9007199254740991; event sequences1..9223372036854775807. Mutation body max16KiB; input decimal max80 characters; fact token max2048 ASCII base64url; reference/reason/label reject NUL and control characters. Proposal patch plus envelope retains the existing total65536-byte budget and max100 submitted money paths for a single existing operation.

- `MoneySubject = {family:'PURCHASE',itemId} | {family:'CUSTOM',itemId,fieldDefinitionId} | {family:'CATALOG',entryId,revision,target:{kind:'ENTRY'}|{kind:'VARIANT',variantId},definitionId}`. Never accept an arbitrary table or JSON path.
- `RawMoney = {amountMinor:string,currency:string}`. V1 DTOs continue their existing safe-number shape; v2 wraps the unchanged record and adds this exact interpretation view.
- `MoneyView = {schemaVersion:1,subject,raw:RawMoney|null,factToken,interpretation}`. Interpretation is `MISSING`, `UNKNOWN{reason:NO_EVIDENCE|RAW_WRITER|REVOKED|ORIGIN_ERASED|EVIDENCE_ERASED}`, or `INTERPRETED{exponent,unitKey,basisId,assertionId,eventId,evidenceCategory:null|OWNER_ATTESTATION|OPERATOR_VERIFIED_RECORD,eligibility:ELIGIBLE|UNIT_UNSUPPORTED,decimal}`. `decimal` is exact ungrouped dot notation; public catalog projection excludes factToken, actor, reference, reason and private evidence category. Unknown has no decimal/exponent/unit default.
- `Authoring = {kind:'DECIMAL',profileId:'legacy-money-iso-2026-09-17-v1',currency,decimal} | {kind:'RAW',profileId:same,currency,amountMinor,exponent,unitKey}`. RAW must match the profile's unit/exponent exactly. Decimal grammar is trimmed digits plus optional one comma OR dot and1..exponent fractional digits; no grouping/sign/scientific notation, no fraction for exponent0. Derive with bigint and enforce safe raw bound. Do not call valuation's grouped-locale parser or browser ICU scale helper.
- `NewMoneyIntent = {op:'NEW',authoring}`; `ExistingMoneyIntent = {op:'RETAIN',expectedFactToken} | {op:'CLEAR',expectedFactToken} | {op:'REPLACE',expectedFactToken,authoring}`. Existing MISSING uses REPLACE with its absence token; NEW is only initial item/custom/proposal creation. Omitted money means untouched, never implicit RETAIN/classify. Correction is REPLACE plus required `correctionReason`1..1000, retained as audit metadata; ordinary replacement does not retract earlier assertions.
- `ClassifyMoneyInput = {expectedFactToken,exponent,unit:{kind:'SUPPORTED',unitKey}|{kind:'UNSUPPORTED',label},evidence:{category,reference?,reason}}`; currency comes from raw fact, never a client correction. `RevokeMoneyInput = {assertionId,expectedAssertionToken,reason}`; it can target an older origin, even after raw replacement. Repeating a retraction conflicts; it does not revoke an independent later assertion. Assertion tokens are canonical base64url strict `{v:1,subject,assertionId,evidenceErasedAt:null|ISOtimestamp,revocationId:null|uuid}` (same2048-byte cap), authorized and compared under the origin subject lock. Private classification-history GETs return these tokens for prior assertions, including superseded generations; ordinary item reads need expose only the current effective assertion.
- Server-only `AuthoringReceipt = {schemaVersion:1,profileId,authorityHash,raw,exponent,unitKey,normalizedDecimal}`. Do not persist the original locale text; the exact normalized amount and immutable parser contract prove prospective meaning. Clients cannot submit a receipt as trusted evidence.
- `MoneyFactTokenV1` is canonical base64url JSON of `{v:1,subject,generation:null|uuid,sequence:string,raw:null|RawMoney,effectiveEventId:null|uuid,originId:null|uuid,revocationId:null|uuid}`. Sequence0 means untouched/no events. Tokens are opaque equality preconditions, not credentials; parse strictly, authorize first, compare every field under the fact lock. No secret/signature service is needed. Include effective origin erasure/revocation state so RETAIN cannot ignore changed evidence.
