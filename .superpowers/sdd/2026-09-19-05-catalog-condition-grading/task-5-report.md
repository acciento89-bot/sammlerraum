## Result and consumer contracts

`createGradingService(database, actorUserId)` supplies `listGradings(itemId)`, `getGrading(itemId, gradingId)`, `addGrading(itemId, input)`, `updateGrading(itemId, gradingId, input)` and `removeGrading(itemId, gradingId)`. Current personally authored records hold provider, normalized display grade, optional exact numeric value and explicit authored scale, optional certificate number, graded date, verification URL, source/provenance, and creation/update timestamps. Multiple records can represent different providers or authored historical dates; no authoritative grade is selected or inferred.

Owner-only routes are GET/POST `/api/v1/items/[itemId]/gradings` and GET/PUT/DELETE `/api/v1/items/[itemId]/gradings/[gradingId]`. POST returns 201 with `{ grading }`; GET/PUT return `{ grading }`, list returns `{ gradings }`, and DELETE returns 204. PUT replaces all facts, so omitted nullable facts become null. Provider and grade remain required. DELETE accepts no body and bounds unexpected bodies before rejecting them. Stream-counted UTF-8 input is limited to 8192 bytes independently of Content-Length. Strict input rejects unknown fields, including ownership, trusted-verification flags and condition bands.

All endpoints require live uncached/unrefreshed sessions and no-store responses; mutations require exact Origin. Domain transactions recheck item and collection ownership/deletion under the shared item row lock. Missing/foreign/deleted items and missing/mismatched/foreign grading IDs produce hidden 404 responses. Archived/disposed items remain owner-readable; all grading mutations reject them with 409. Certificate, capacity and physical-quantity conflicts have stable domain codes and 409 route mapping. Public item DTOs and catalog/proposal payloads remain free of grading and private provenance.

## Identity, normalization and authored numeric semantics

- Provider/grade are NFC-normalized and trimmed, maximum 120 characters; internal whitespace is preserved. Optional certificate is similarly normalized/trimmed, maximum 160 characters, preserving leading zeros, case, punctuation and internal whitespace. Controls are rejected. Provider identity applies generic ASCII case folding only; certificate identity is exact after the documented normalization. No provider aliases or provider-specific number equivalences are invented.
- Unique `(ownerId, providerKey, certificateKey)` applies to current stored rows, never to all accounts globally. Same-owner/same-provider certificate duplication conflicts; different providers or different owners may independently store the same number. PostgreSQL NULL uniqueness permits multiple records without a certificate. Update/removal releases the old current certificate identity.
- Optional numeric input is a decimal **string**, never a JS number. Strict unsigned syntax allows at most eight integer and four fractional digits, range 0 through 99999999.9999, without exponent, rounding or automatic grade conversion. An explicit nonempty authored `comparableScale` (maximum 120 characters) is required exactly when numeric value is present. Neither value nor scale establishes trusted comparability, provider equivalence, or quality ordering. No cross-provider conversion/ranking is implemented.
- Storage is `Decimal(12,4)`; DTOs read the database value as exact decimal text, e.g. `10.0000`. Strict application validation prevents precision loss. Direct database writes retain PostgreSQL's native numeric precision behavior; named checks enforce nonnegative, paired-scale and finite upper bounds.
- Optional real calendar date uses YYYY-MM-DD. Optional source is bounded to 1000 characters. Verification URL is bounded to 2048 characters and accepts HTTP(S) without credentials/control characters. No URL is fetched, no provider is contacted, and authenticity or real provider verification is never claimed.

## Physical specimen policy and retention costs

Every current grading record requires item quantity=1, including records without certificates. Users split a quantity item into individual specimens before grading. Current records are capped at 100 per item under the item lock. `updateItem` now rejects quantity changes when grading exists; its existing quantity=1 and unrelated edits still work. `splitQuantityItem` explicitly rejects grading-bearing rows before any copy, so a certificate is never silently cloned or moved. Removing all current grading records releases the quantity restriction.

Native enforcement uses the item composite unique index `(id, ownerId, quantity)`, grading's constant `itemQuantity=1` named CHECK, and composite ownership/quantity FK with **ON UPDATE RESTRICT** and ON DELETE CASCADE. Direct SQL and racing quantity changes cannot leave a current grading on a quantity greater than one. Tests observe PostgreSQL lock waits in both service directions and in a direct native-FK race.

Root explicitly ruled that **item soft deletion preserves grading rows and owner-scoped certificate reservations**. The hidden item becomes 404; re-entering the same certificate under the same owner/provider conflicts, while another account remains independent. This prevents silent erasure of personal facts. Remove grading before deleting the item to release the claim now. Recovery of retained items and later permanent erasure belong to Phase 09 trash/restore policy; no recovery endpoint was added here.

There is no bespoke immutable grading history or generic audit framework. Current edits/removal are personal CRUD with timestamps. Phase 09 Task 4 must append grading audit events inside these existing mutation transactions. This task makes no immutable-history guarantee. Category/exact condition and grading remain independent; condition changes preserve grading and grading removal preserves exact condition.
