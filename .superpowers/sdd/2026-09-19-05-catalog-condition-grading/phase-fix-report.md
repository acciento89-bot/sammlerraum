## CI integration appendix — archive versus an older item snapshot

Base: `fdd1753db409ac3a65386df7094e263505a15209`. This is the separately ruled new CI defect in the existing Phase 03 ItemForm path, after the completed Phase 05 fix review. Root authorized a bounded diagnosis first, then the proven race fix and its newly introduced refresh-failure boundary. No earlier review findings were reopened.

Root retained both outcomes in `phase-ci-fdd1753-*` evidence; those root-owned files are excluded from this commit. The local deterministic probes below establish the intermittent product race without replacing either CI outcome.

Diagnosis (`logs/phase-ci-archive-diagnosis-01.log`) used real responses and persisted lifecycle facts. Holding an actual post-save GET captured `archivedAt:null`. Save had already settled to enabled before Archive. Archive then returned HTTP 200, the actual DB/API both had an archive timestamp, and Save became disabled. Delivering the older GET re-enabled Save while archive success remained visible and the persisted item stayed archived. This reproduced in DE desktop and EN mobile (two desired-invariant failures). A separate control held a real HTTP 200 tags-PUT acknowledgement after the edited heading appeared: Save was still disabled, Archive was available, archive persisted, and releasing that acknowledgement left Save disabled (two passes). The heading alone is early readiness, but waiting for saving alone does not prevent the stale initialization race.

The source change is confined to ItemForm plus one DE/EN error-copy entry. A generation guards initialization and explicit snapshot reads. Successful core/archive acknowledgements invalidate older reads before applying their authoritative item response. The initializer's entire item-scoped snapshot application—item, metadata, collection/node, known item ID, identifiers and initial location—is shared with a guarded fresh actor-bound GET after successful writes. Cancelled/superseded initialization results, errors and loading finalization cannot apply. Superseded refresh results/errors also cannot apply. This protects lifecycle state and retains the same item's acknowledged metadata without schema, service, permission, caching-framework or write-retry changes. Cost: one additional read after an acknowledged core save or archive when that generation is still current.

The new read boundary explicitly preserves write acknowledgement. If a current core-save refresh fails, the form retains the known item ID and existing retry-without-duplicate status instead of navigating away; the bounded localized error says the changes were saved but details could not refresh. Retrying is an explicit user action and PATCHes that known ID. An archive-refresh failure leaves its acknowledged archive response/status and read-only controls intact. A failed read never rolls back, retries or recasts an acknowledged server write as unacknowledged.

Permanent regressions replace the temporary diagnostic probes. Four DE/EN × desktop/mobile cases hold an actual older active-item GET through real archive acknowledgement, verify HTTP 200 plus DB/API archive truth, release that exact response, and assert the main/read-only notice, core controls and sibling condition/grading controls remain read-only. They also verify the just-saved Edition metadata survives the rejected old snapshot via the fresh actor-bound snapshot. Two project-locale cases inject an HTTP 503 only for the follow-up read after a real 201 create, verify retained acknowledgement/known ID, explicitly retry as exactly one PATCH with exactly one item in the DB, then inject another read 503 after real archive acknowledgement and verify lifecycle, metadata and disabled controls remain correct. The original core archive assertion is unchanged. No assertion/timeout/permission relaxation, `.first()`, skip or automatic write retry was introduced. The old metadata-acknowledgement control remains evidence, not permanent diagnostic noise.
