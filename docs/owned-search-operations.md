# Owned search: explicit duplicate filters

The `duplicate` Boolean leaf reads actual private `DuplicateRelation` declarations written by the wishlist/duplicate service. A true match requires a marked pair with two live items and live collections that still belong to the requesting owner. False is the two-valued complement after outer authorization. Similar titles, catalog mappings and quantity alone do not create a duplicate flag. Multiple overlapping pairs never multiply item summaries or the pre-cursor item count.

The request lifecycle restricts candidate items. An explicitly marked partner may be active, archived or disposed while its record remains live and owned, matching the existing Phase10 declaration semantics. Deleted partners or parents are excluded. Actual ownership transfer permanently retires the old private declarations; restoration does not infer/recreate them.

Rows, pre-cursor counts, saved-query resolution and dashboard selected item/unit counts use the same bounded RepeatableRead selection and compiler. Saved definitions store the predicate, not the marks or an authorization receipt, so a fresh resolution sees current marks and ownership. The dashboard's separate `ALL_LIVE_OWNED_PAIRS` statistic counts pairs across the owner's whole live inventory; it is intentionally different from matched item counts.

No membership, public visibility or granular share grants access to someone else's private duplicate declarations. The current search scope remains server-fixed OWNED; the separately required shared-search authorization integration is not implied by this filter. Existing fresh authentication, no-store responses, strict AST and closed errors remain intact. Market controls remain disabled by default and independent market rights are unchanged; canonical-money coverage gates remain unchanged.

Native synthetic 1/50/500-item fixtures retain real count/page `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` plans with existing indexes. Each true/false request makes five data reads and11 instrumented raw calls including timeout configuration, independent of item count. Driver BEGIN/COMMIT are not included in that measurement. No per-item producer calls, schema/index changes or timeout changes are introduced. Existing12s total, up to three complete serialization attempts,5s transaction,2s statement and500ms lock budgets remain the operational bounds; sample timings are not production guarantees.
