# Private owner-authored milestones

H1 provides storage/contracts/domain only. HTTP routes and the localized editor/list panel follow as H2/H3; no existing public endpoint is claimed here.

Each record is private content supplied by its owner: a title and a real Gregorian calendar date. `dateBasis: OWNER_ENTERED` explicitly distinguishes the entered date from actual server `createdAt` / `updatedAt` recording times. Past/future dates0001–9999 are allowed. There is no inferred achievement, verified badge, inventory association, money metric, activity ledger or backfill. This list is independent of inventory text/filter/lifecycle, labelled `ALL_PERSONAL_MILESTONES`.

`createPersonalMilestoneService(database)` offers `createMilestone(actor,input)`, `updateMilestone(actor,id,input)`, `deleteMilestone(actor,id,input)` and `listMilestones(actor,input?)`. The authenticated actor supplies ownership; input cannot supply owner/id/timestamps. A title is NFC/trim with1–120Unicode codepoints and maximum480UTF8bytes; controls/NUL/unpairedsurrogates are rejected. Interior whitespace and compatibility characters are preserved. The date is a date-only string, never converted through local timezone or Date.UTC's0–99year coercion.

The additive table starts empty, has a cascading User owner FK, finite date/timestamp checks, canonical title constraints, revision1–2147483647 and one owner/dateDESC/createdAtDESC/idDESC index. Existing migrations and user facts remain unchanged. Deletion is permanent; account deletion cascades. No audit/trash/exactly-once HTTP creation is promised.

Update and delete require expectedRevision. Full title/date replacement increments revision even for equal values. Missing and foreign IDs both return the same MILESTONE_NOT_FOUND; owned stale/max revision returns MILESTONE_CONFLICT. The owner-scoped initial lookup takes a row lock before producing an edit timestamp; the subsequent CAS still verifies the revision/affected row. A blocked successful edit records server time after that wait; a real lock timeout rolls the operation back. The shared bounded transaction preserves only the branded milestone error class, not arbitrary matching error codes.

List defaults20, maximum50 and preview5. Three fixed data statements read server clock, exact safe count and limit+1 rows in one RepeatableRead snapshot. The canonical bounded2048-character body cursor binds owner/version/limit/sort and exact date/createdAt/UUID tuple. Every page rechecks ownership. Later pages are fresh snapshots; edits can move records across pages, so refresh starts again. All returned rows including the sentinel are validated; malformed retained projections fail closed. No inventory scan or N+1 reads are involved.

Existing transaction limits remain12s overall/at most3recognized serialization retries/5s transaction/2s acquisition+statement/500ms lock, with shrinking settings and checks after settlement. Actual wrapper calls, excluding driver BEGIN/COMMIT controls: create3(1data), update/delete5(2data), list7(3data). Create allocates a UUID once outside internal retries. Response bytes are capped at64KiB; the largest valid50row DTO is proven below that cap, rather than inventing a valid native overflow. Unknown outcomes after settlement are not false rollback assurances.

Native proof uses guarded PostgreSQL17.11 `sammlerraum_test`, synthetic owners only.13native cases cover real private authoring, date extremes, foreign/missing access, revision races, true deletion/cascade, three-field paging with ties, snapshot consistency during a committed writer, fixed query counts, direct SQL constraints, real lock waiting/timeout and bounded5000record owners. Actual1/50/500row analyzed fixture plans are retained; these are not a production capacity or stale-statistics guarantee. Driver-corruption/dependency/retry/settlement cases are separately labelled simulations. Do not disable constraints to fabricate corrupt retained rows.
