# Reviewed production deployment through Portainer

This is a prepared runbook, **not** evidence of a live deployment. Source stays on the existing draft branch until the recorded release approval. Production deployment, live provider activation and Search Console DNS changes require the separate authorization recorded in the V1 ledger. Finish the source, review and exact-CI gates first.

## Prepare a concrete candidate

Record the exact reviewed Git commit, successful CI link, immutable **web/worker/migration** image digests built from that same commit, PostgreSQL17 image digest, current deployed image digests for application rollback, and the existing persistent database/uploads volume names. Never use a moving `latest`/branch tag. Local `sha256:<image-id>` is supported only on the host that actually has that exact built image; transfer/publish reviewed images to the existing private registry and use distribution digests for Portainer. Registry provisioning or new credentials are not part of this source change.

Use `docker-compose.prod.yml` on the existing standalone Docker environment. Confirm Portainer's Compose implementation honors `service_completed_successfully`; otherwise run the **same** one-shot migration job manually and keep web/worker stopped until it exits0. Do not bypass the migration gate or use an unsupported stack mode. The migration image contains tooling; the public standalone web image does not install packages on startup.

Inspect and retain existing named volumes. Do not rename a production volume to make an empty installation appear healthy. On a genuinely new installation, create and record new volumes deliberately. Both apps use the same persistent uploads volume; PostgreSQL has its own volume. No host source-code bind mounts or public database/worker ports. The web port is loopback-only behind the existing HTTPS reverse proxy, which must route the verified public hostname and present a valid certificate. TLS/DNS/proxy authorization and actual public checks remain mandatory before launch.

## Private configuration

Keep interpolation values in a protected host/Portainer environment, never Git/chat/CI output. `SAMMLERRAUM_ENV_FILE` is the private application environment file on the Docker host; provide it through Portainer's supported secret/environment mechanism without exposing its contents. On Portainer setups where host env files are unavailable, render and apply the equivalent private environment through Portainer, then validate the privately resolved JSON before rollout. Do not paste a raw resolved config into a public issue; it contains secrets.

Required interpolation: `SAMMLERRAUM_WEB_IMAGE`, `SAMMLERRAUM_WORKER_IMAGE`, `SAMMLERRAUM_MIGRATION_IMAGE`, `SAMMLERRAUM_DB_IMAGE`, `SAMMLERRAUM_DB_VOLUME`, `SAMMLERRAUM_UPLOADS_VOLUME`, `SAMMLERRAUM_ENV_FILE`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `DATABASE_URL`, `SAMMLERRAUM_MIGRATION_APPROVED_SHA`. The database URL must use the stack DB service/credentials, and all services must refer to the same database. Optional loopback web port defaults to3000.

The app environment must satisfy `.env.example` and the validated server/auth configuration: real application origin, auth secret, verified OAuth configuration, required SMTP verification/reset transport, uploads path, explicit whole `BILLING_PLAN_LIMITS`, billing environment and approved product/provider policy. There are no hidden production quota/price defaults. Credentials alone never approve paid ingestion or analysis. The **source-ready initial stack verifier requires** `BILLING_ENABLED`, `AI_ANALYSIS_ENABLED`, `MARKET_SYNC_ENABLED`, `SCRYDEX_ENABLED`, `PRICECHARTING_ENABLED` and `NOTIFICATION_EMAIL_ENABLED` all explicitly `false`. Enabling any later is a separately reviewed and authorized configuration change with real rights, keys, billing and delivery checks; do not weaken the gate to make it green. Auth verification/reset SMTP is independently required for actual account use and needs real delivery proof before public signup.

## Backup, drain, migrate, roll out

Use a maintenance window. Prevent new writes, drain/stop all old web/worker writers (including pre-staging-lock builds) and keep PostgreSQL/volumes intact. Produce and **actually restore-test** a private backup of the currently deployed version. The new backup tool expects the current V1 table contract; for an older deployed schema, use its verified recovery procedure and original app version, not an invented waiver of missing-table errors. Record the trusted backup manifest SHA256, recovery proof and recovery location outside public hosting.

Set `MIGRATION_MODE=production`, `SAMMLERRAUM_BACKUP_MANIFEST_SHA256` to the actual verified manifest digest, and `SAMMLERRAUM_MIGRATION_APPROVED_SHA` to the reviewed40-character commit. The digest/commit inputs are operator attestations bound into the deployment configuration; syntax alone does **not** prove that a backup was tested. Source review and the operator's actual recovery evidence remain required. The migration runner holds a DB advisory lock and invokes the already installed frozen Prisma migrations. It logs only controlled outcomes. Failed/timed-out migrations keep rollout stopped. Investigate migration history and active operations before retry; never mark a failed migration applied merely to continue.

Privately render `docker compose -f docker-compose.prod.yml config --format json` and run `python3 scripts/verify-production.py --config-json /private/resolved.json`. This is the static gate. Run the one-shot migration before starting either app. Both app services also depend on successful migration and healthy PostgreSQL. Start the pinned candidate, wait for container health, then run `bash scripts/verify-production.sh --health-url https://sammlerraum.de/api/health` with the same private Compose configuration. Verify worker health inside its container and the actual production SQL server major17. Finally run the separate public smoke/release checks. Do not declare an environment operational from config validation alone.

Application and database containers have finite CPU/memory/PID limits; read-only app roots use bounded temporary filesystems, and only uploads persist. The worker has a12-minute stop grace period to let bounded jobs settle. Size resources against the host and the documented media/import limits before changing them. Alert on repeated OOM/forced termination; do not increase retries to conceal it.

## Failure and rollback

Retain the verified backup and previous image digests. Stop a failed candidate and inspect controlled logs privately. A backward-compatible application rollback can switch to the recorded previous images without removing volumes **only if** those versions are compatible with the applied schema. There is no automatic reverse migration. An incompatible schema failure requires a separately authorized full recovery to isolated replacement resources from a proven backup and deliberate traffic switch. Never overwrite the only good database or uploads copy. Do not delete persistent volumes during deployment, verification or rollback.

## CI evidence and limits

`scripts/test-production-stack.sh` runs only inside GitHub Actions, using run-unique synthetic volumes, the actual built immutable image IDs and a fresh `_test` database. It renders/validates the stack, runs real migrations, starts both applications, checks HTTP/database/worker health and writes scoped synthetic restart receipts to DB/uploads. It restarts both apps and verifies both receipts remain. It stops containers normally and leaves the named volumes intact until the disposable runner itself is removed. The same job also runs the actual PostgreSQL17 backup/restore drill. These are production-like **test** receipts; they do not prove live Portainer, TLS, SMTP, OAuth, provider or customer readiness.
