# Explicit personal money writers (M3)

The private money protocol uses schemaVersion1 and explicit authoring profiles under `/api/v1/money/...`; V2 is a service-contract label, not another REST namespace. Existing raw CRUD remains accepted and produces UNKNOWN through native invalidation. Current UI/capability and canonical consumer cutover are M5/M6, not enabled here.

Create accepts `{schemaVersion:1,item:<strict nonmoney create fields>,purchase?:NEW}`. Omission means no purchase, not zero. Update accepts strict nonmoney fields plus optional RETAIN/REPLACE/CLEAR. Raw purchase field names are rejected in these envelopes. Every existing-money intent has an actual equality precondition; omission and RETAIN omit raw column names from the shared existing writer. REPLACE always obtains the actual native new generation, even for equal values, and appends the independently revalidated pinned AUTHOR receipt in the same transaction. CLEAR/readd does not revive an earlier token or interpretation.

Existing create/update/custom transaction bodies are reused; legacy public methods retain their original validators and transaction ownership. Explicit authoring validates its strict nonmoney input and pinned receipt before using those bodies, without allowing changing runtime Intl data to override the pinned profile. All owner/parent locks remain in shared bodies. The legacy custom writer now explicitly checks both item and collection ownership, complementing the native composite FK. The test of an inconsistent owner tuple is correctly rejected by the existing FK, not a newly claimed exploit.

The personal service owns one bounded ReadCommitted transaction (5s transaction,2s statement,500ms lock,2s acquisition;12s total/at most3 recognized serialization attempts). It never commits a raw write separately from AUTHOR metadata. Unknown commit/dependency failures are not retried as mutations. Actual elapsed time is checked after settlement as well as inside the callback. Resolved-money adapters retain the identity of the one actual active transaction.

The existing quantity split captures each present source purchase/custom fact under its real source locks, creates the child through the original workflow, reads each actual trigger-assigned child generation and appends flattened COPY within that same transaction. Missing values need no asserted copy; unknown values remain unknown. Per-unit amount4 with quantity10 stays total40 when split3+7. Private media, identifiers, tags, locations and other typed custom fields keep their existing workflow; valuation history stays on the original. Any failed COPY rolls back source quantity and child.

Private history uses strict sequence+id keysets, default20/max50, canonical subject-bound cursors, bounded projected fields and a1MiB response cap. Every page rechecks actual owner/item/collection/custom-definition scope; no token grants authority. Only original AUTHOR/CLASSIFY entries offer their fresh historical revocation precondition. Audit fields are recorded history, never a borrowed current MoneyView or an assertion of eligibility. Financial/evidence history is never added to the public item whitelist.

Eight thin paths provide11operations: create; itemGET/PATCH; customPUT; purchase+requested customGET(max50unique IDs); purchase/custom classificationPOST+historyGET; purchase/custom revocationPOST. Fresh auth disables cookie cache/refresh. Mutations require exact Origin; GET permits ordinary same-origin browser requests without an Origin header while rejecting an explicitly foreign Origin. URL grammar, duplicate/unknown fields, stream-counted16KiB bodies, fatalUTF8/BOM rejection and nested duplicate-key/Unicode checks precede mutation. The existing shared bounded scanner/copier is reused; no parallel JSON parser. Responses/errors use no-store/request IDs and closed messages without raw input/cause echoes. Existing split routes map branded money conflicts rather than arbitrary lookalike payloads.

No production deployment or full money/V1 completion is implied. The applied M2 SQL migration is unchanged by M3.

Accepted optional purchase/custom correctionReason is retained on the original AUTHOR event as private audit text. The forward-only author_correction_audit migration extends native content guards without modifying applied M2. Self-erasure and actual UserFK erasure remove this human note and actor together while preserving the machine receipt/eligibility; an actor-only removal that would orphan a note is rejected. Copies do not duplicate the private note. History cursor sequences are bounded to signed bigint before SQL, including max/max+1 transport coverage.
